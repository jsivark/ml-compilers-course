Part I · Foundations

01C

The compiler you build later emits C, so you must read and write it without hesitation. Pointers, arrays, structs, the heap and the build toolchain underlie every later kernel.

about 45–65 h · difficulty ●●○○○

StepsBuildProjectHelpGo deeper

After this module you can

  • Write multi-file C programs with pointers, structs and malloc/free that run clean under ASan, UBSan and valgrind.
  • Implement a hash table in C and draw its memory layout.
  • Build a tree-walking interpreter (parser plus evaluator) in C.
  • Build every C project with make and -Wall -Wextra -g -fsanitize=address,undefined.

Steps

Work through these in order. Each step points at one specific unit.

  1. Watch

    CS50 week 1: your first C programs

    Watch at 1.5x if you already program. Focus on compiling with clang, types and printf format specifiers.

  2. Do

    CS50 problem set 1: Mario (more comfortable) and Credit

    Do the 'more comfortable' versions; they need nested loops and integer digit arithmetic.

  3. Watch

    CS50 week 2: arrays

    Focus on strings as char arrays ending in '\0', and on argc/argv.

  4. Do

    CS50 problem set 2: Caesar (or Substitution)

    Implement it, then rebuild with -fsanitize=address and introduce an out-of-bounds read to see what ASan reports.

  5. Watch

    CS50 week 4: memory and pointers

    Pointers, malloc/free, stack vs heap, valgrind. Watch all of it.

  6. Read

    Beej's Guide to C, ch. 5-7: pointers, arrays, strings

    Type out each example and predict its output before running it.

  7. Read

    Beej's Guide to C, ch. 8, 11, 12: structs, pointer arithmetic, malloc and free

    Pointer arithmetic here is the same idea as tensor strides in Module 7.

  8. Do

    CS50 problem set 4: Filter (less comfortable) and Recover

    Filter is 2-D array indexing over pixels; Recover is raw byte I/O with fread. Do both.

  9. Watch

    CS50 week 5: data structures

    Linked lists, trees and hash tables built from structs and pointers.

  10. Do

    CS50 problem set 5: Speller (build a fast hash table)

    Write the hash table. valgrind must report zero leaks; compare your timing against the staff solution.

  11. Build

    Build Your Own Lisp, ch. 6-10: write a small interpreter in C

    Chapters 6 Parsing through 10 Q-Expressions, including the bonus marks. This is your first tree-walking interpreter.

Build

  1. Build Your Own Lisp through ch. 10 Q-Expressions, with a REPL that evaluates (eval (head {(+ 1 2) 3})).
  2. A generic open-addressing hash map in C (string keys, void* values, resize at 0.7 load) plus a test file inserting 1M keys, compiled with -Wall -Wextra -fsanitize=address,undefined and running clean.

Portfolio project: kiln v0.1: an arena-allocated tensor core in C

kiln, the main project · v0.1 adds the C core every later version runs on · next: v0.2

Start kiln with a small C library, tcore, that stores N-dimensional float32 tensors (shape, strides, offset, data) in an arena allocator, with elementwise add and mul, a naive matmul and a C test suite. Every later kiln version builds on it, and the C your compiler generates in Part III will link against it. Benchmark creating and freeing 10^4, 10^5 and 10^6 tensors of 16, 256 and 4096 floats with the arena vs malloc/free, and explain the difference. Time each case with your kbench tool from Module 0.

Deliverables

  • repo with tcore.h/tcore.c, a Makefile, and tests that run clean under ASan, UBSan and valgrind
  • README with a table and plot of allocation throughput (arena vs malloc) across tensor counts and sizes
  • a 600–1200 word write-up explaining your memory layout, ownership rules, and why arenas suit compiler-generated code

Rubric

Solid
All tests pass under sanitizers with zero leaks; arena benchmark reported with at least 3 sizes and repeated runs; API documented in the header.
Exceptional
Randomized property tests that compare tcore results against NumPy, benchmark results reported as median and interquartile range, and CI that runs the sanitizer build on every push.

References: Beej's Guide to C Programming

Help

If you get stuck

  • Returning a pointer to a local array: the array lives in the returning function's stack frame and is invalid after return. Re-watch the stack vs heap part of CS50 Week 4.
  • sizeof on an array parameter gives the pointer size, because the array decays to a pointer when passed. Pass the length explicitly (Beej ch. 6 Arrays).
  • Off-by-one on strings: allocate strlen(s)+1 for the terminating '\0'.
  • A bug that disappears when you add printf is usually undefined behaviour. Build with -Wall -Wextra -g -fsanitize=address,undefined while developing.
  • mpc parse errors are hard to read: print the AST with mpc_ast_print before debugging your evaluator.

Ready to move on when

  • Draw stack and heap for a function that mallocs an int array, returns it and the caller frees it.
  • Explain why sizeof(arr) differs inside and outside a function that receives arr.
  • Explain p[i], *(p+i) and i[p], and what pointer arithmetic does on an int* vs a char*.
  • Speller passes check50 and valgrind reports 0 bytes lost.
  • ASan and UBSan are silent on your hash map test.
Reference implementations (4)

Make a real attempt first. When you are stuck, or after you finish, compare your work with these.

  • Build Your Own Lisp: the author's source code (Build (1): Build Your Own Lisp ch. 6-10)
    Daniel Holden's repo for the book, with the per-chapter source files; diff your chapter 6-10 code against them.
  • ht: a small hash table in C (Ben Hoyt) (Build (2): generic open-addressing hash map)
    A small, readable open-addressing hash table in C with FNV-1a hashing and resizing, plus tests and benchmarks.
  • Ben Hoyt, How to implement a hash table (in C) (Build (2) and Problem Set 5: Speller)
    The write-up for ht: linear probing, resize policy and a timing comparison against a binary search approach.
  • chibicc: a small C compiler to read (Project: tcore code style reference)
    A complete C11 compiler written in clean C with one commit per feature; a model of idiomatic C data structures such as linked lists, tokens and string handling.

Talks, papers, code and writing (16)

Talks

  • Enter The Arena: Simplifying Memory Management (2023) · Ryan Fleury
    The talk version with scratch arenas and temporary memory; watch for the API patterns tcore can copy.
  • How I program C · Eskil Steenberg
    A long, opinionated talk on writing large C programs; focus on the naming, memory and debugging sections.
  • Data-Oriented Design and C++ (CppCon 2014) · Mike Acton (CppCon)
    Argues that data layout, not code, determines performance; this mindset drives tensor layout choices later.
  • Designing and Evaluating Reusable Components (2004 talk) · Casey Muratori
    Muratori on API design for C libraries (granularity, retained vs immediate); apply it to tcore's public API.

Videos

  • Tips for C Programming · Nic Barker
    A 35-minute tour of modern C99 habits (designated initializers, clear typedefs, simple build layout, avoiding include tangles) aimed at people coming from higher-level languages.

Blogs and articles

  • Untangling Lifetimes: The Arena Allocator · Ryan Fleury
    The clearest case for arenas over malloc/free; read the whole post before designing tcore's allocator.
  • Memory Allocation Strategies (series) · Ginger Bill
    Implements linear, stack, pool and free-list allocators in C step by step; part 2 (linear/arena) maps onto the project.
  • An easy-to-implement, arena-friendly hash map · Chris Wellons (nullprogram)
    A hash trie that lives in an arena with no resizing; compare its trade-offs with your open-addressing map.
  • Examples of quick hash tables and dynamic arrays in C · Chris Wellons (nullprogram)
    Short arena-backed hash trie and dynamic array implementations you can copy and adapt; compare them with your own hash table from this module.
  • Compiler Options Hardening Guide for C and C++ · OpenSSF Best Practices WG
    Maintained table of GCC/Clang warning and hardening flags with rationale; use the warnings section to choose your project's default CFLAGS and note which flags conflict with sanitizers.
  • Clang Hardening Cheat Sheet - Ten Years Later · Quarkslab
    Concrete Clang flags and what each one catches at compile time or run time; read the warnings and sanitizer parts alongside the module's debugging exercises.

Code to read

  • stb: single-file C libraries to read and reuse · Sean Barrett
    Production C libraries in single headers; read stb_ds.h to see a generic dynamic array and hash map done with macros.

More reading

  • cstack, Let's Build a Simple Database, parts 1-8 — Pager and B-tree in C.
  • c4: a C compiler in four functions — Keep for Module 12; skim now.
  • Beej's Guide to C, ch. 17: projects with many files — Headers, separate compilation, the linker.
Stretch project
