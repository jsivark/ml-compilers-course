Part III · The Course · 10-411 week 13

30Final project: build and iterate

Implement the core idea in small measured steps, keeping a log of what did not work; negative results are part of the report.

about 50–80 h · difficulty ●●●●●

StepsBuildProjectHelpGo deeper

After this module you can

  • Attribute your result to specific changes with an on/off ablation table.
  • Show profiler evidence for every optimization you kept.

Steps

Work through these in order. Each step points at one specific unit.

  1. Implement

    Core implementation, smallest version

    Get the simplest end-to-end version through the harness, correct first.

  2. Measure

    Profile where time goes

    Use Nsight Compute (GPU) or perf (CPU) to find the bottleneck before each change.

  3. Read

    Scaling Book: roofline

    Compute arithmetic intensity and the roofline bound for your target so you know the ceiling.

  4. Implement

    Iterate: one change per commit

    Each change: hypothesis, measurement, kept or reverted, logged.

  5. Test

    Regression suite

    All course tests plus project correctness tests on every iteration.

  6. Measure

    Ablations

    Turn each optimization off individually and measure contribution.

  7. Implement

    Keep a public lab notebook

    Dated entries: hypothesis, profile evidence, result, keep/revert. Negative results included.

Build

The core project implementation with measured iterations and ablations.

Portfolio project: Capstone phase 2: lab notebook and ablations

Capstone

Implement the core idea through the harness and keep a public lab notebook: every experiment with hypothesis, profile evidence, result and decision. Finish with a full ablation table and a mid-point update post.

Deliverables

  • repo with tagged commits for each milestone and a LAB_NOTEBOOK.md with 15+ dated entries
  • ablation table: each component on/off with mean and variance
  • plots: metric over iterations, roofline position before and after
  • a 600–1200 word mid-project update (blog post or forum thread) with current numbers and open problems

Rubric

Solid
Beats or matches the baseline on the primary metric with ablations explaining the gain; all regression tests pass.
Exceptional
Clear win over a strong public baseline, or a negative result with a root cause; at least one issue or PR filed upstream.

References: Nsight Compute Profiling Guide, Karpathy, A Recipe for Training Neural Networks

Help

If you get stuck

  • Optimizing without profiling: always record the profiler evidence that motivated a change.
  • Many changes per commit: you will not know what helped. One change, one measurement, one log line.
  • Ignoring negative results: log them; they are part of the report and show judgment.
  • Correctness drifts silently: run the full test suite on every iteration, including the interpreter cross-check from module 19.
  • Stuck on one bottleneck for more than two days: log what you tried, ask in GPU MODE or tinygrad Discord, or switch to the stretch goal.

Ready to move on when

  • Core implementation runs correctly through the harness
  • Results vs baseline recorded
  • Experiment log includes failed attempts
  • All course tests still pass
Reference implementations (4)

Make a real attempt first. When you are stuck, or after you finish, compare your work with these.

  • modded-nanogpt records (Iterate: one change per commit)
    Each record is a commit with a measured change and a log; a public example of one-change-per-commit iteration.
  • siboehm/SGEMM_CUDA (Ablations)
    Ten kernels each building on the last with a benchmark script; shows how to structure incremental, ablatable optimizations.
  • gpt-fast (Ablations)
    Under 1000 lines where each speedup (torch.compile, int8, speculative decoding, tensor parallel) is a flag you can toggle; a template for an ablation table.
  • tinygrad process_replay.py (pinned) (Regression suite)
    Regression checking by replaying and diffing generated kernels; adapt it for your regression suite.

Go deeper (optional)

Talks, papers, code and writing (12)

Blogs and articles

  • The USE Method · Brendan Gregg
    Check utilization, saturation and errors for every resource before guessing; apply it to SMs, memory bandwidth and PCIe.
  • Performance Analysis Methodology · Brendan Gregg
    A catalog of methods and anti-methods (streetlight, random change); use it to justify each profiling step in your notebook.
  • Accelerating Generative AI with PyTorch II: GPT, Fast · PyTorch team (Horace He et al.)
    A worked iteration log from 25 to 240+ tokens/s, one technique at a time with numbers; copy its write-up format.
  • Outperforming cuBLAS on H100: a Worklog · Pranjal Shankhdhar
    A kernel-by-kernel worklog with TFLOPS after every step; a model for a public lab notebook.
  • How to Scale Your Model · Austin, Douglas, et al. (Google DeepMind)
    Beyond the roofline chapter, the transformer and inference chapters give the FLOP and byte counts you need to place each iteration on the roofline.
  • Modal GPU Glossary · Modal
    Look up each Nsight Compute metric you cite (occupancy, warp stalls, memory throughput) with clear explanations.
  • Systems Benchmarking Crimes · Gernot Heiser
    Use it to audit your ablation table for missing variance, cherry-picked shapes and improper baselines.
  • Outperforming cuBLAS on NVFP4 · cudaforfun (Substack)
    A 2025 step-by-step worklog building an NVFP4 GEMM in CUDA and inline PTX; study how each iteration is motivated by a measurement, the pattern your build log should follow.
  • Measuring Computer Systems is Almost Certainly Harder Than You Think · Cornell CS 6120 course blog
    A student discussion of the measurement-bias paper; use its checklist while iterating so each speedup you log is a real effect and not noise.
  • Statistically rigorous Java performance evaluation (The Morning Paper) · Adrian Colyer
    A short summary of the Georges et al. method; focus on how many repetitions to run and when two configurations are actually different.
  • ThunderMLA: FlashMLA, but faster and simpler · Hazy Research (Stanford)
    A compact iterate-and-measure worklog on a decode megakernel; study how they find the bottleneck (tail effects, launch overhead) and fix it step by step.

Problem sets

  • KernelBench · Stanford Scaling Intelligence Lab
    Run your compiler across its level 1-3 problems as a broad regression and speedup suite beyond your chosen target.
Stretch project

Submit your optimized kernel to a GPU MODE leaderboard (gpumode.com) and place in the top 10 for its problem, or show a reproducible speedup over the current top entry. Document every submission in the lab notebook with its measured time.
