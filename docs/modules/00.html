Start here · Orientation

00Orientation and toolkit

Every later module assumes you can use a terminal, version your work with git, debug C, rebuild a Python environment, read papers and, above all, measure performance honestly. From Module 4 to the end, almost every project ends in a speed claim, so this module has you build the small benchmark tool you will use for all of them. The repo you create here, kiln, holds every module's work.

about 12–18 h · difficulty ●○○○○

StepsBuildProjectHelpGo deeper

After this module you can

  • Write shell pipelines and small bash scripts, locally and over ssh.
  • Use git branches and tags, and recover from a bad merge with git reflog.
  • Compile C with -g and -fsanitize=address and find a crash with gdb or lldb.
  • Rebuild your Python environment from a lockfile.
  • Benchmark a program with warmup, repeated runs and a recorded environment, and report a median with its spread.

Steps

Work through these in order. Each step points at one specific unit.

  1. Watch

    Missing Semester: get comfortable in the shell

    Use the terminal on macOS or Linux. On Windows, set up WSL2 first (next step) and work inside it. Do the exercises at the bottom of the page.

  2. Do

    Set up a Unix-like environment (macOS, Linux or Windows)

    macOS: run xcode-select --install for clang, make, git and lldb, then install Homebrew for everything else. Linux: install the build tools with your package manager, e.g. sudo apt install build-essential clang gdb git (Debian/Ubuntu) or sudo dnf install gcc clang gdb git make (Fedora). Windows: run wsl --install (this page), then follow the Linux line inside WSL and keep your course files under ~/ in the Linux filesystem, not /mnt/c, or builds will be slow.

  3. Watch

    Missing Semester: the command-line environment

    Pipes, environment variables, job control and dotfiles. Pay attention to environment variables: the project's experiment changes nothing but the environment and measures the effect.

  4. Watch

    Missing Semester: set up your editor and tools

    You do not need to switch editors. Set up your main editor with clangd (C) and a Python language server, and learn enough Vim to edit a file over ssh.

  5. Watch

    Missing Semester: how Git works

    Understand the data model (blobs, trees, commits, refs) rather than memorizing commands.

  6. Do

    Learn Git Branching: interactive Git practice in the browser

    Do the Introduction Sequence on the Main tab and the first two levels on the Remote tab. Interactive drills for commit, branch, merge, rebase and remotes. Then use one branch per module and tag each finished module.

  7. Watch

    Missing Semester: debugging and profiling

    printf debugging, debuggers, sanitizers and profilers. Modules 1-4 use all of these.

  8. Do

    Learn to use a debugger (LLDB on Mac, GDB on Linux)

    Make sure clang (or gcc) and make work. Compile a buggy program with -g -O0 -fsanitize=address, then set a breakpoint, step, print a variable and get a backtrace. Use lldb on macOS (it ships with the Command Line Tools) and gdb on Linux or WSL (gnu.org/software/gdb/documentation); the commands map almost one to one.

  9. Read

    Makefile Tutorial: write a small Makefile

    Read Getting Started, Targets, Variables and Phony targets. That is enough for the project's make test and make bench targets.

  10. Do

    Set up Python environments with uv

    Create one project environment for kiln with numpy, matplotlib and pytest (PyTorch comes later, in Module 7). Commit uv.lock. The project's kbench.py and its tests run in this environment.

  11. Read

    Python argparse tutorial: give your script command-line options

    Read up to 'Short options'. kbench needs -n, --warmup and everything after -- as the command (nargs=argparse.REMAINDER). For running that command and capturing its output, read the subprocess.run section of docs.python.org/3/library/subprocess.html.

  12. Read

    pytest: write and run your first tests

    Read the whole page (about 15 minutes). The project's tests/test_kbench.py uses plain assert and, for the CSV test, the tmp_path fixture shown there.

  13. Read

    Matplotlib quick start: make your first plot

    Read up to 'Styling Artists'. You need one line plot with error bars (ax.errorbar), axis labels and fig.savefig.

  14. Read

    S. Keshav, How to Read a Paper

    A short paper. Use the three-pass method on each paper in this course and keep a one-paragraph summary per paper in your repo.

  15. Read

    Mytkowicz et al., Producing Wrong Data Without Doing Anything Obviously Wrong!

    The ASPLOS 2009 paper showing that the size of your environment variables and the link order can change a benchmark's speed enough to flip a conclusion. Read sections 1-4; the project asks you to reproduce the environment-size effect.

  16. Read

    LLVM benchmarking tips: how to get stable timings

    A short page from the LLVM developers on reducing noise: fixed CPU frequency, pinning to a core, quiet machine. Apply what your OS allows and record what you could not control.

  17. Do

    hyperfine: a command-line benchmarking tool

    Install it (brew install hyperfine on macOS, sudo apt install hyperfine on Debian/Ubuntu) and time any command with hyperfine --warmup 3 'cmd'. Your own tool in the project does the same job; use hyperfine to check its numbers.

  18. Read

    GitHub Actions quickstart: run checks on every push

    Make the demo workflow run once, then write your own ci.yml. To install uv and run pytest in CI, follow docs.astral.sh/…/github.

  19. Do

    Start a learning log (Julia Evans, write a brag document)

    Keep LOG.md in kiln with one dated entry per session: what you did, what confused you, what you will do next. This is your only log; write one short public post per module from it. The easiest place to publish is GitHub Pages (quickstart: pages · quickstart on GitHub).

Build

The kiln repo described in the project below: README, LOG.md, a Makefile, a sanitized C test and a pytest, green in GitHub Actions, plus bench/kbench.py and the environment-size experiment.

Portfolio project: kiln v0.0: the repo and a benchmark tool you will use all course

Setup project

kiln is the one repo for this whole course. It grows into a small ML library with its own compiler: tensors in Module 1, autograd in Module 6, a graph IR in Module 8, and from Module 19 the course compiler (./compile) becomes its backend. Module exercises and skill projects go in labs/NN-name/ inside the same repo. In this module you set it up and build kbench, a small timing tool, then use it to reproduce a real result: changing only the size of the environment can change how fast a program runs.

Steps

  1. Create a public GitHub repo named kiln with these files and folders: README.md, LICENSE (MIT is fine), LOG.md, Makefile, bench/, labs/00-setup/, tests/, and the pyproject.toml and uv.lock from the uv step.
  2. In labs/00-setup/, write sum.c: fill an array of 10 million ints with small values (for example i % 100), add them into a long long total (an int total would overflow), and print it. Make it take about 0.1-0.5 s; if it is faster, repeat the loop. In the Makefile add two targets: make sum builds ./sum with -O2 for timing, and make test builds a separate ./sum_asan with -g -fsanitize=address,undefined, runs it and checks the printed total.
  3. Write bench/kbench.py. Running python bench/kbench.py -n 20 --warmup 3 -- ./sum should run the command 3 times without timing it, then 20 times timing each run with time.perf_counter() around subprocess.run, and append one row to results.csv. Add a --label option whose text is stored in the row, so you can tell runs apart later. The row holds: the command, number of runs, median, min, max, the interquartile range (the spread of the middle half of the runs: statistics.quantiles(times, n=4) gives the quartiles), the git commit (git rev-parse --short HEAD), the compiler version (first line of cc --version), the OS (platform.platform()) and the CPU model (platform.processor(), or sysctl -n machdep.cpu.brand_string on macOS, /proc/cpuinfo on Linux). Then add make bench, which builds ./sum and runs kbench on it; let make bench RUNS=3 set -n so CI can run a quick version.
  4. Write tests/test_kbench.py with pytest. Put the median and interquartile-range math in plain functions so you can test them on fixed lists such as [1, 2, 3, 4, 100], and check that one run writes a CSV row with every column filled.
  5. Time the same ./sum with hyperfine (hyperfine --warmup 3 -N ./sum). The two medians should agree within a few percent; if not, find out why. Note both numbers in labs/00-setup/README.md.
  6. The experiment: in a bash loop, for N in $(seq 0 64 4096), run python bench/kbench.py -n 20 --warmup 3 --label $N -- env "PAD=$(head -c $N /dev/zero | tr '\0' x)" ./sum. Each run adds a dummy environment variable of N x's; keep the quotes, or the shell may mangle it. That is 65 sizes and takes about 10 minutes. Then write a short Python script that reads results.csv, takes the rows with these labels, and plots median time (min and max as error bars) against N into labs/00-setup/env_size.png.
  7. Write about one page in labs/00-setup/README.md: what you measured, the plot, whether the change across N is bigger than the run-to-run spread, and what you could not control (other apps, laptop power mode, CPU frequency). The paper saw its effect with variables on the stack; if you see nothing, say so and show the noise. An honest null result passes.
  8. Add .github/workflows/ci.yml (start from the GitHub Actions C starter workflow in Go deeper) that on every push installs uv, then runs make test, uv run pytest, and make bench RUNS=3 as a quick check that the tool still works. Do not trust timings from CI machines.
  9. Publish one short post (500-1000 words) on GitHub Pages, a blog or similar: what kiln will become, your study schedule, and your environment-size result with the plot. Link it from the README.

Deliverables

  • public kiln repo with the layout above, all green in GitHub Actions
  • bench/kbench.py with its pytest, checked against hyperfine
  • labs/00-setup/README.md with the environment-size plot and write-up
  • LOG.md with at least 3 dated entries, and one published post linked from the README

Rubric

Solid
CI is green; kbench reports median, min, max and interquartile range and records the environment; it agrees with hyperfine; the plot exists and the write-up compares the effect to the noise honestly.
Exceptional
Also pins the process to one core and fixes the CPU frequency where the OS allows (Linux taskset and cpupower), repeats the experiment with link order changed (the paper's second effect), and gives a bootstrap confidence interval for each median.

References: Mytkowicz et al., Producing Wrong Data Without Doing Anything Obviously Wrong!, hyperfine: a command-line benchmarking tool, LLVM benchmarking tips

Help

If you get stuck

  • WSL slow or files missing: keep the repo under ~/ in Linux, not /mnt/c; open it with code . from WSL.
  • macOS 'gdb' won't run: use lldb, which ships with the Xcode Command Line Tools; the commands map almost one to one (lldb's GDB-to-LLDB command map helps).
  • git 'detached HEAD' or a messy merge: run git status and git log --oneline --graph --all before anything else; git reflog can recover almost anything.
  • Limit tooling setup (dotfiles, themes) to two evenings, then start Module 1.
  • Pip and conda in the same env cause mysterious import errors: pick one tool (uv recommended) and one env per project.
  • Timings jump around between runs: close other apps, plug in the laptop, run more repetitions and report the spread. On macOS you cannot pin cores or fix the frequency; record that in the README instead of hiding it.

Ready to move on when

  • Write a one-line shell pipeline that prints the 5 largest files under a directory.
  • Explain the difference between a commit, a branch and a tag in git's data model.
  • Use gdb or lldb to find the line of a segfault in a 20-line C program without adding printfs.
  • Recreate your Python environment from scratch from your lockfile alone.
  • Explain why you report the median of many runs instead of a single run or the mean, and what warmup runs are for.
  • Name two things outside your code that can change its measured speed, and how you controlled or recorded each.
