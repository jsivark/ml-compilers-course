00Orientation and toolkit

Every later module assumes you can use a terminal, version your work with git, debug C, rebuild a Python environment and read papers efficiently. Set this up once here so it does not slow you down later. The repo you create holds every module's work.

about 10–15 h · difficulty ●○○○○

StepsBuildProjectHelpGo deeper

After this module you can

  • Write shell pipelines and small bash scripts, locally and over ssh.
  • Use git branches and tags, and recover from a bad merge with git reflog.
  • Compile C with -g and -fsanitize=address and find a crash with gdb or lldb.
  • Rebuild your Python environment from a lockfile.
  • Read a paper with Keshav's three-pass method and write a five-sentence summary.

Steps

Work through these in order. Each step points at one specific unit.

  1. Watch

    Missing Semester lecture 1: get comfortable in the shell

    Use the terminal on macOS or Linux. On Windows, set up WSL2 first (next step) and work inside it. Do the exercises at the bottom of the page.

  2. Do

    Set up a Unix-like environment (macOS, Linux or Windows)

    macOS: run xcode-select --install for clang, make, git and lldb, then install Homebrew for everything else. Linux: install the build tools with your package manager, e.g. sudo apt install build-essential clang gdb git (Debian/Ubuntu) or sudo dnf install gcc clang gdb git make (Fedora). Windows: run wsl --install (this page), then follow the Linux line inside WSL and keep your course files under ~/ in the Linux filesystem, not /mnt/c, or builds will be slow.

  3. Watch

    Missing Semester lecture 2: shell tools and scripting

    Focus on pipes, find, grep and writing a small bash script with set -euo pipefail. Later modules use scripts like this for benchmark sweeps.

  4. Watch

    Missing Semester lecture 3: learn a text editor (Vim)

    You do not need to switch to Vim. Learn enough to edit files over ssh on a remote machine, and set up your main editor with clangd and a Python language server.

  5. Watch

    Missing Semester lecture 6: how Git works

    Understand the data model (blobs, trees, commits, refs) rather than memorizing commands.

  6. Do

    Learn Git Branching: interactive Git practice in the browser

    Do the Introduction Sequence on the Main tab and the first two levels on the Remote tab. Interactive drills for commit, branch, merge, rebase and remotes. Then use one branch per module and tag each finished module.

  7. Read

    Pro Git book, ch. 2-3, 7.3 and 7.10: basics, branching, stashing and debugging

    Use as a reference when something goes wrong. Learn git log --oneline --graph, git stash and git bisect.

  8. Watch

    Missing Semester lecture 7: debugging and profiling

    Covers printf debugging, gdb and pdb, perf and flame graphs. Modules 1-4 use all of these.

  9. Do

    Learn to use a debugger (LLDB on Mac, GDB on Linux)

    Make sure clang (or gcc) and make work. Compile a buggy program with -g -O0 -fsanitize=address, then set a breakpoint, step, print a variable and get a backtrace. Use lldb on macOS (it ships with the Command Line Tools) and gdb on Linux or WSL (gnu.org/software/gdb/documentation); the commands map almost one to one.

  10. Do

    Set up Python environments with uv

    Create one project environment with numpy, matplotlib, pytest and torch (the CPU build is enough). Commit uv.lock or requirements.txt.

  11. Read

    S. Keshav, How to Read a Paper

    A short paper. Use the three-pass method on each paper in this course and keep a one-paragraph summary per paper in your repo.

  12. Read

    Julia Evans, How to ask good questions

    Before asking anyone for help, write down what you tried, the exact error and a minimal reproduction.

  13. Do

    Join the GPU MODE community

    A Discord server for GPU kernel and ML systems work; its talks are also on YouTube. Read the pinned messages before posting.

  14. Do

    Start a learning log (Julia Evans, write a brag document)

    Keep LOG.md in your repo with one dated entry per session: what you did, what confused you, what you will do next. Write a short public post at the end of each module.

Build

A public GitHub repo ml-compilers-log with a README (goals, schedule, hardware), LOG.md, a modules/ directory, a Makefile target that compiles and runs a sanitized C hello-world, a pytest that passes, and a GitHub Actions CI workflow that runs both on every push.

Portfolio project: Set up the kiln repo, your notes site and a first post

Setup project

Create a public repo named kiln with a README, a license, a Makefile and a CI workflow that builds and runs an empty test, plus a notes site or blog where you will write one page per module. kiln is the main project of this course: a small ML library with its own compiler, grown one version at a time from Module 1 to Module 39. Publish a first post saying what you are building and why.

Deliverables

  • repo with README, LOG.md, Makefile, a sanitized C test and a pytest, all green in GitHub Actions
  • a short CONTRIBUTING-style note to yourself: branch-per-module, commit message conventions, how to tag a finished module
  • a 600–1000 word blog post on your goals and plan, linked from the README

Rubric

Solid
CI passes on push; README states the plan; LOG.md has at least 3 dated entries; blog post is published and linked.
Exceptional
Reproducible environment (uv.lock or a devcontainer) that CI builds from scratch, and a make bench target that writes timings to CSV for use in later modules.

References: Missing Semester 2020, Lecture 6: Version Control (Git)

Help

If you get stuck

  • WSL slow or files missing: keep the repo under ~/ in Linux, not /mnt/c; open it with code . from WSL.
  • macOS 'gdb' won't run: use lldb, which ships with the Xcode Command Line Tools; the commands map almost one to one (lldb's GDB-to-LLDB command map helps).
  • git 'detached HEAD' or a messy merge: run git status and git log --oneline --graph --all before anything else; git reflog can recover almost anything.
  • Limit tooling setup (dotfiles, themes) to two evenings, then start Module 1.
  • Pip and conda in the same env cause mysterious import errors: pick one tool (uv recommended) and one env per project.

Ready to move on when

  • Write a one-line shell pipeline that prints the 5 largest files under a directory.
  • Explain the difference between a commit, a branch and a tag in git's data model.
  • Use gdb or lldb to find the line of a segfault in a 20-line C program without adding printfs.
  • Recreate your Python environment from scratch on a clean machine (or container) from your lockfile alone.
  • Summarize a paper after Keshav's first pass in five sentences (the five Cs).

Courses

  • The Missing Semester of Your CS Education (2026 lectures) · Anish Athalye, Jon Gjengset, Jose Javier Gonzalez Ortiz (MIT)
    The January 2026 rewrite of the course; the debugging/profiling and packaging lectures are new, so read those even if you know the 2020 version.

Books

  • How to Scale Your Model · Google DeepMind (Austin et al.)
    The roofline-first view of LLM training and inference on TPUs and GPUs; read Part 1 (Rooflines) as a preview of the course's goal.

Blogs and articles

  • Inside .git · Julia Evans
    Walks through the actual files in .git so the blob/tree/commit model from Lecture 6 becomes concrete.
  • Wizard Zines · Julia Evans
    Short illustrated guides; the free comics on git, perf, strace and debugging are worth printing.
  • Linux perf Examples · Brendan Gregg
    The reference page for perf one-liners; focus on perf stat, perf record and perf report.
  • Flame Graphs · Brendan Gregg
    How flame graphs are built and read, by their inventor; read the CPU flame graph section.
  • Latency Numbers Every Programmer Should Know · Jonas Boner (from Jeff Dean and Peter Norvig)
    The table of cache, memory, disk and network latencies to memorize before Modules 3-4.
  • ARCHITECTURE.md: why every repo needs a short code map · Alex Kladov (matklad)
    Short argument for a codemap file in every repo; add one to ml-compilers-log now.
  • A Recipe for Training Neural Networks · Andrej Karpathy
    Its habit of small verified steps applies to compiler work too; read the 'become one with the data' and 'overfit' sections.
  • GPU Glossary · Modal
    A linked glossary of GPU hardware and software terms; skim the Device Hardware section now to see where the course ends up.
  • Profiling in PyTorch (Part 1): A Beginner's Guide to torch.profiler · Hugging Face
    Shows the wait/warmup/active schedule and how to read the exported trace; a good first exposure to GPU profiling before the course reaches kernels.
  • AI Flame Graphs · Brendan Gregg
    Extends CPU flame graphs to show GPU/accelerator instruction samples under the full software stack; read it to see where the flame graph idea goes once kernels are involved.
  • The Secret Rules of the Terminal (zine) · Julia Evans
    Links the free blog posts behind the zine (PATH, pipe buffering, escape codes); read the linked posts to fix the confusing terminal behaviour beginners hit.

Code to read

  • The Art of Command Line · Joshua Levy
    A dense one-page list of shell habits; work through the Everyday use and Processing files and data sections.
  • build-your-own-x: an index of from-scratch tutorials · CodeCrafters community
    An index of from-scratch tutorials; bookmark the Programming Language, Database and Neural Network sections for side projects.
  • GitHub Actions starter workflow for a C project built with Make
    The official minimal workflow that runs make on every push; compare it with your own CI file.
  • GitHub Actions starter workflow for a Python project
    Official workflow that installs dependencies and runs pytest; shows the job and step layout your CI needs.
  • gdb-dashboard: a more readable GDB screen
    A single .gdbinit that shows registers, source, stack and memory at each stop; a reference for a productive gdb setup.
  • samply: a simple CPU profiler for Mac, Linux and Windows · Markus Stange (Mozilla)
    A sampling CPU profiler for Linux, macOS and Windows that opens results in the Firefox Profiler UI; use it as a lower-friction alternative to perf + flamegraph scripts for the profiling exercises.
  • PyTorch profiling tutorial · Quentin Anthony
    Practical walkthrough of torch.profiler and Nsight traces on real training code; focus on how to read a trace timeline and spot CPU launch overhead versus GPU work.
Stretch project

Build a reproducible dev environment for the whole course: a Dockerfile or Nix flake that pins clang, gdb, perf, Python and uv, plus a CI matrix (Linux x86-64 and macOS arm64) that builds and tests every module directory. Measure cold-start setup time on a fresh machine and get it under 10 minutes, documented in the README.
