00Orientation and toolkit

Every later module assumes you can drive a terminal, version your work, debug C, manage Python environments, read papers and ask good questions. An afternoon of setup here saves weeks of friction, and your public repo becomes the portfolio that gets you hired.

about 6–10 h · difficulty ●○○○○

After this module you can

  • After this module you can work comfortably in a Unix shell, including on a remote machine over ssh.
  • After this module you can manage work with git branches, tags and CI, and recover from common mistakes.
  • After this module you can compile C with sanitizers and debug it in gdb/lldb, and reproduce a Python environment.
  • After this module you can read a research paper with a structured three-pass method and ask questions that get answered.

Steps

Work through these in order. Each step points at one specific unit.

  1. Watch

    Missing Semester 2020, Lecture 1: Course overview + the shell

    On Windows, install WSL2 Ubuntu first (next step) and do everything inside it. Do every exercise at the bottom of the page.

  2. Do

    Install WSL2 (Windows only)

    Run `wsl --install`, then keep your course files inside the Linux filesystem (~/), not /mnt/c, or builds will be slow. macOS users: install Xcode Command Line Tools and Homebrew instead.

  3. Watch

    Missing Semester 2020, Lecture 2: Shell Tools and Scripting

    Focus on pipes, find/grep/rg, and writing a small bash script with set -euo pipefail. You will script benchmark sweeps constantly.

  4. Watch

    Missing Semester 2020, Lecture 3: Editors (Vim)

    You need not switch to Vim; learn enough to edit on a remote GPU box over ssh. Set up VS Code (or your editor) with clangd and a Python language server.

  5. Watch

    Missing Semester 2020, Lecture 6: Version Control (Git)

    Understand the data model (blobs, trees, commits, refs) rather than memorizing commands.

  6. Do

    Learn Git Branching: Main levels 1-4 and Remote levels 1-2

    Interactive drills for branch, merge, rebase, and push/pull. Then adopt a workflow: one branch per module, small commits with descriptive messages, tag each finished module.

  7. Read

    Pro Git, ch. 2 Git Basics and ch. 3 Git Branching

    Reference for when something goes wrong. Learn `git log --oneline --graph`, `git bisect` and `git stash`.

  8. Watch

    Missing Semester 2020, Lecture 7: Debugging and Profiling

    Covers printf debugging, gdb/pdb, perf and flame graphs, all of which recur in Modules 1-3 and the GPU modules.

  9. Do

    C toolchain + debugger: GDB docs or the LLDB tutorial

    Install clang (or gcc) and make. Compile a buggy program with -g -O0 -fsanitize=address, then set a breakpoint, step, print a variable and get a backtrace. Linux users can use gdb instead (https://www.gnu.org/software/gdb/documentation/).

  10. Do

    Python environment with uv (or venv)

    Make one project environment with numpy, matplotlib, pytest and torch (CPU build is fine). Commit a lockfile or requirements.txt so your results can be reproduced.

  11. Read

    S. Keshav, How to Read a Paper

    Two pages. Use the three-pass method on every paper in this course; keep a one-paragraph summary per paper in your repo.

  12. Read

    Julia Evans, How to ask good questions

    Then join the GPU MODE Discord (next step). State what you tried, the exact error, and a minimal reproduction before asking.

  13. Do

    Join the GPU MODE community

    The main community for kernels and ML systems; the reading-group lectures are also on YouTube. Lurk first, read pinned messages, ask in the right channel.

  14. Do

    Start a learning log

    Keep LOG.md in your repo with one dated entry per session: what you did, what confused you, what you'll do next. Write a public blog post at the end of each module; explaining things is how you find gaps in your understanding.

Build

A public GitHub repo `ml-compilers-journey` with a README (goals, schedule, hardware), LOG.md, a modules/ directory, a Makefile target that compiles and runs a sanitized C hello-world, a pytest that passes, and a GitHub Actions CI workflow that runs both on every push.

Portfolio project: Public course repo + first blog post

Set up the repository that will hold every module's work and portfolio project for the whole course, with CI from day one. Publish a first blog post (GitHub Pages, a personal site, or similar) titled something like 'Why I'm building an ML compiler from scratch', stating your goals, your starting point, and a dated plan for the course.

Deliverables

  • repo with README, LOG.md, Makefile, a sanitized C test and a pytest, all green in GitHub Actions
  • a short CONTRIBUTING-style note to yourself: branch-per-module, commit message conventions, how to tag a finished module
  • a 600–1000 word blog post on your goals and plan, linked from the README

Rubric

Solid
CI passes on push; README states the plan; LOG.md has at least 3 dated entries; blog post is published and linked.
Exceptional
Reproducible environment (lockfile or devcontainer), a `make bench` placeholder that writes results to CSV for later modules, and a blog post that someone else in GPU MODE or online found useful enough to comment on or share.

If you get stuck

  • WSL slow or files missing: keep the repo under ~/ in Linux, not /mnt/c; open it with `code .` from WSL.
  • macOS 'gdb' won't run: use lldb, which ships with the Xcode Command Line Tools; the commands map almost one to one (lldb's GDB-to-LLDB command map helps).
  • git 'detached HEAD' or a messy merge: run `git status` and `git log --oneline --graph --all` before anything else; `git reflog` can recover almost anything.
  • Do not over-polish the tooling (dotfiles, themes). Two evenings is enough; move on to Module 1.
  • Pip and conda in the same env cause mysterious import errors: pick one tool (uv recommended) and one env per project.

Ready to move on when

  • Write a one-line shell pipeline that prints the 5 largest files under a directory.
  • Explain the difference between a commit, a branch and a tag in git's data model.
  • Use gdb or lldb to find the line of a segfault in a 20-line C program without adding printfs.
  • Recreate your Python environment from scratch on a clean machine (or container) from your lockfile alone.
  • Summarize a paper after Keshav's first pass in five sentences (the five Cs).
