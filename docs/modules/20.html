20Loops, floats, runtime; matmul and conv

range and end turn straight-line code into loop nests, and placing each computation in the innermost loop it depends on is the first scheduling decision. f32 arrives, so correctness becomes a tolerance.

about 25-35 h · difficulty ●●●●○

After this module you can

  • Lower range/end into C for loops with each node in the innermost loop it depends on.
  • Compare f32 results within a stated tolerance and explain why accumulation order changes them.
  • Hand-write GEMM (256^3) and a 3x3 conv in UIR, verify them against NumPy, and report a GFLOP/s baseline.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: Week 3

    RANGE/END/RECIP, the ranges and ended_ranges properties, and the note that this is likely the first week you need a rewrite engine to order the ranges.

  2. Implement

    range/end/recip/f32 in parser, types and bounds

    range n has bounds [0, n-1]; recip takes f32 only; float literals contain '.'. REJECT rejected_recip_int and rejected_range_index_oob.

  3. Implement

    Compute a ranges property per node

    For each node, the set of open ranges it depends on: the union over its sources, minus ranges closed by end. This decides loop placement.

  4. Implement

    Render ranges as nested for loops

    Emit each node inside the innermost loop among its ranges; close loops at end, innermost first. Pass range_fill, range_square, nested_ranges_2x3, float_recip.

  5. Read

    Goldberg, What Every Computer Scientist Should Know About Floating-Point Arithmetic: 'Rounding Error' and 'Relative Error and Ulps'

    Enough to justify a 1e-4 relative tolerance and to see why summation order changes a float result.

  6. Implement

    Float comparison in assert and runtime

    Compare f32 results with a tolerance; emit float, not double, and render recip x as 1.0f/x.

  7. Implement

    Hand-write gemm_256.uir

    M=N=K=256 with three ranges and an accumulator buffer. Check against NumPy (A @ B in float32) within 1e-4 with a small harness script.

  8. Read

    CS231n conv notes: 'Implementation as Matrix Multiplication'

    The im2col paragraph in the Convolutional Layer section. Write the six-loop direct conv on paper first.

  9. Read

    tinygrad-notes: The trick in convolution and arange

    tinygrad builds conv from _pool, which is expand, permute and shrink. Preview for Module 22; the note uses an older tinygrad API.

  10. Implement

    Hand-write conv3x3.uir

    Direct 3x3 conv2d, 1 channel, 32x32 input, no padding (30x30 output), as nested ranges. Check against a NumPy loop or scipy.signal.correlate2d(mode='valid') within 1e-4.

  11. Measure

    Time gemm_256 in C

    Report GFLOP/s (2*256^3 flops / median time over 10+ runs after a warmup) for your naive loop nest. Module 24 tries to beat this number.

  12. Test

    10 own tests

    E.g. a range of size 1, an index that is safe only because of range bounds, recip of a negative, an expression that should be placed outside the inner loop.

Build

Loop nests from range/end, f32 and recip, plus hand-written GEMM and conv UIR checked against NumPy.

Portfolio project: Roofline benchmark harness for your compiler

Build a harness that runs the kernels your compiler can emit now (elementwise add over 2^20 f32, gemm at 64/128/256/512, conv3x3 at 32/64/128) over a size sweep, computes arithmetic intensity (flops / bytes of buffers) from the IR, and plots each on a roofline of your machine using a measured peak FLOP/s and a STREAM-style copy bandwidth. Later modules add their kernels to it.

Deliverables

  • repo with a bench CLI that writes JSON results keyed by git commit
  • a generated HTML or notebook page: roofline plot, GFLOP/s vs size, history across commits
  • the two microbenchmarks (peak FLOP/s, memory bandwidth) and their measured numbers
  • a 600-1200 word write-up on which kernels are compute- or memory-bound and why

Rubric

Solid
All listed kernels on one roofline with intensity computed from the IR, not hand-entered; repeated runs agree within 5%; NumPy float32 matmul shown as a reference point.
Exceptional
CI flags any kernel that slows down by more than 5% between commits; adds an L1/L2 bandwidth ceiling and explains which gemm sizes fall out of cache.

References: How to Scale Your Model: All About Rooflines, Simon Boehm, Fast Multidimensional Matrix Multiplication on CPU from Scratch

If you get stuck

  • Wrong loop nesting or off-by-one bounds: print the generated C for nested_ranges_2x3 and trace it by hand.
  • conv3x3 wrong only at the edges: output size for a valid 3x3 on 32x32 is 30x30. Check your index ranges against that.
  • gemm_256 fails the tolerance: the oracle used float64. Compute the NumPy reference in float32, or compare with a relative tolerance.
  • Timings vary run to run: warm up once, time 10+ runs and report the median.

Ready to move on when

  • python3 run_tests.py 1, 2 and 3 all pass
  • gemm_256.uir matches NumPy float32 matmul within 1e-4
  • conv3x3.uir matches a NumPy 3x3 valid correlation within 1e-4
  • In the generated C, a node that depends only on the outer range is emitted outside the inner loop
