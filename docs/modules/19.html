19Loads, stores, memory; render C

Memory introduces effects, so graph order is no longer free: a load must be ordered after the stores it observes. This module is also your first real backend: toposort, emit C, compile with clang, call through ctypes.

about 20–30 h · difficulty ●●●○○

After this module you can

  • After this module you can topologically order a UOp graph and emit straight-line C from it.
  • After this module you can compile generated C at runtime with clang and call it through ctypes with NumPy buffers.
  • After this module you can use an interpreter as a reference to cross-check a code generator.
  • After this module you can reason about pointer types, alignment and aliasing in generated code.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: Week 2

    Read the Week 2 section (BUFFER/LOAD/STORE/AFTER, 'loads and stores must be fully ordered') and the README Week 2 spec side by side.

  2. Implement

    Parse nested (op ...) expressions and new ops

    Extend the parser for extern, store, load, after, index-on-buffer, and nested parenthesised operands anywhere an atom goes. Week 1 tests must still pass.

  3. Read

    Russ Cox, Hardware Memory Models: sections 'Sequential Consistency' and 'x86-TSO'

    Only these two sections; the point is why compilers/hardware reorder unordered memory ops, motivating AFTER.

  4. Read

    Preshing, Memory Ordering at Compile Time

    Short: how a compiler reorders loads/stores and what a compiler barrier is.

  5. Implement

    Ordering validator

    Track, per buffer, the stores reachable through after; REJECT unordered loads and out-of-range or dtype-wrong stores (reuse Week 1 bounds). Pass rejected_load_without_after, rejected_store_oob, rejected_store_dtype.

  6. Implement

    Interpreter support for memory

    Extend the Week 1 evaluator with buffers so it executes store/load/after in dependency order. Pass store_load, index_store, two_stores_ordered, read_modify_write, mismatch_stale_read.

  7. Read

    tinygrad linearize (toposort to a list)

    Read linearize() and UOp.toposort (https://github.com/tinygrad/tinygrad/blob/b91fe2773cbc1a33c38c90b55c835e26be42a335/tinygrad/uop/ops.py#L281) to see how a graph becomes a straight-line program.

  8. Implement

    Toposort + C emitter

    Emit one loopless C function: one local per node in topo order, buffers as pointer args, int32_t with wrapping semantics (cast through uint32_t to avoid UB).

  9. Read

    tinygrad renderer/cstyle.py: base_rewrite and ClangRenderer

    Read base_rewrite (lines 9-82) and ClangRenderer (line 283): rendering is just another PatternMatcher from UOp to string.

  10. Read

    Python ctypes: loading shared libraries and arrays

    Sections 'Loading dynamic link libraries', 'Arrays' and 'Specifying the required argument types'. (Or dlopen if not Python.)

  11. Implement

    clang -O2 -shared + ctypes runtime

    Write .c to a temp dir, compile, dlopen, allocate buffers, call, compare to assert. All week01 and week02 tests through the C backend.

  12. Test

    Cross-check the two backends

    Run interpreter and C on every test and diff results; add 10 tests (e.g. two stores to the same index, store whose index is only safe via mod bounds, signed overflow that clang would treat as UB).

Build

A C backend: toposort, render one loopless function, compile with clang, run via ctypes, with the interpreter as a cross-check.

Portfolio project: Differential fuzzer: compiler vs interpreter vs NumPy

Build a random UIR program generator (Csmith-style, with shapes, dtypes and edge-case constants) and differential-test your C backend against your interpreter and a NumPy oracle. Add automatic test-case reduction so every mismatch shrinks to a minimal reproducer that you commit as a regression test.

Deliverables

  • repo with a generator, an oracle runner and a delta-debugging reducer
  • README with fuzzing throughput (programs/s), coverage of op types, and a bug table (found, root cause, fix commit)
  • a regression corpus of minimized failing programs wired into the test suite
  • a 600–1200 word write-up on the most surprising bug and what it taught you about C semantics

Rubric

Solid
Runs 1M+ random programs with no unexplained mismatches; at least 5 real bugs found, minimized and fixed in your compiler.
Exceptional
Generator is grammar- or Hypothesis-driven with a coverage feedback loop; reduced cases average under 10 nodes; you find a bug in a real tool (e.g. a clang fast-math or NumPy dtype corner) and report it upstream.

References: Csmith: random program generator for differential compiler testing, Hypothesis documentation (property-based testing)

If you get stuck

  • Segfaults from ctypes: argument types not declared (argtypes) or a non-contiguous NumPy array. Use np.ascontiguousarray and set argtypes.
  • Results differ by tiny amounts: clang with -ffast-math reorders floats. Compare with a tolerance, or drop fast-math while debugging.
  • Same node rendered twice or used before defined: your toposort is not visiting shared children once. Memoize by node identity.
  • Stale .so loaded: dlopen caches by path. Name the library by a hash of the source.
  • Integer overflow silently UB in C: use explicit int32/uint32 casts that match your interpreter's semantics.

Ready to move on when

  • python3 run_tests.py 2 and 1 pass through the C backend
  • Unordered loads and out-of-range stores are REJECTED
  • Interpreter and C backend agree on all tests
  • 10+ new tests in tests/week02

Going deeper (optional)

  • Russ Cox, Programming Language Memory Models — Follow-up on how languages expose ordering.
  • John Regehr, A Guide to Undefined Behavior in C and C++ — Why your generated i32 adds need care.
