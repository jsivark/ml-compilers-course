19Loads, stores, memory; render C

Memory adds effects, so graph order stops being free: a load must come after the stores it observes. This is also your first backend: toposort, emit C, compile with clang, call through ctypes.

about 20-30 h · difficulty ●●●○○

After this module you can

  • Reject a UIR program whose loads are not ordered after the stores to the same buffer.
  • Toposort a UOp graph, emit one loopless C function, build it with clang -O2 -shared and call it through ctypes.
  • Use the Week 1 interpreter as a reference to diff against the C backend on every test.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: Week 2

    Read the Week 2 section (BUFFER/ALLOC/SHRINK/LOAD/STORE/AFTER; 'Loads and stores must be fully ordered for programs to be valid') next to the README Week 2 spec, which names the buffer op extern.

  2. Implement

    Parse nested (op ...) expressions and new ops

    Extend the parser for extern, store, load, after, index-on-buffer, and nested parenthesised operands anywhere an atom goes. Week 1 tests must still pass.

  3. Read

    Russ Cox, Hardware Memory Models: 'Sequential Consistency' and 'x86 Total Store Order (x86-TSO)'

    Only these two sections. They show why unordered memory operations can be observed out of order, which is what AFTER rules out.

  4. Read

    Preshing, Memory Ordering at Compile Time

    Short post: the compiler reorders loads and stores at -O2, and a compiler barrier stops it.

  5. Implement

    Ordering validator

    Track, per buffer, the stores reachable through after. REJECT unordered loads and out-of-range or wrong-dtype stores, reusing Week 1 bounds. Pass rejected_load_without_after, rejected_store_oob, rejected_store_dtype.

  6. Implement

    Interpreter support for memory

    Extend the Week 1 evaluator with buffers so it executes store/load/after in dependency order. Pass store_load, index_store, two_stores_ordered, read_modify_write, mismatch_stale_read.

  7. Read

    tinygrad linearize (toposort to a list)

    Read linearize() and UOp.toposort (https://github.com/tinygrad/tinygrad/blob/b91fe2773cbc1a33c38c90b55c835e26be42a335/tinygrad/uop/ops.py#L281) to see a graph turned into a straight-line list.

  8. Implement

    Toposort + C emitter

    Emit one loopless C function: one local per node in topo order, buffers as pointer arguments, i32 add/mul/shl done in uint32_t and cast back so signed overflow is not undefined behaviour.

  9. Read

    tinygrad renderer/cstyle.py: base_rewrite and ClangRenderer

    Read base_rewrite (lines 9-80) and ClangRenderer (line 283). Rendering is another PatternMatcher, from UOp to string.

  10. Read

    Python ctypes: loading shared libraries and arrays

    Tutorial sections 'Loading dynamic link libraries', 'Specifying the required argument types (function prototypes)' and 'Arrays'. Use dlopen if your compiler is not in Python.

  11. Implement

    clang -O2 -shared + ctypes runtime

    Write the .c file to a temp dir, compile with clang -O2 -shared, load it, allocate buffers, call, compare with the assert. Run week01 and week02 through the C backend.

  12. Test

    Cross-check the two backends

    Run the interpreter and the C backend on every test and diff the results. Add 10 tests, e.g. two stores to the same index, a store whose index is only safe via mod bounds, an add that overflows INT_MAX.

Build

A C backend: toposort, render one loopless function, compile with clang, run via ctypes, with the interpreter as a cross-check.

Portfolio project: Differential fuzzer: C backend vs interpreter

Write a random UIR program generator for the Week 1-2 op set (i32/bool, scalars and stacks, stores and loads with after, edge-case constants like INT_MIN and 0) and differential-test your C backend against your interpreter. Shrink every mismatch to a minimal reproducer and commit it as a regression test.

Deliverables

  • repo with a generator, a runner that compares both backends, and a delta-debugging reducer
  • README with programs per second, per-op coverage counts, and a table of bugs found (root cause, fix commit)
  • a regression corpus of minimized failing programs wired into run_tests.py-style tests
  • a 600-1200 word write-up on the most surprising bug and the C rule behind it

Rubric

Solid
100,000+ generated programs (batch many functions per .c file to keep clang time down) with no unexplained mismatch; every mismatch found is minimized below 15 nodes and fixed.
Exceptional
Generator is driven by Hypothesis strategies so shrinking is automatic; you compare its shrunk cases against your own reducer; generated programs hit every op and every REJECTED rule at least 100 times.

References: Csmith: random program generator for differential compiler testing, Hypothesis documentation (property-based testing)

If you get stuck

  • ctypes segfault: argtypes not set, or a buffer object freed before the call. Set argtypes and keep a Python reference to every buffer.
  • Node rendered twice or used before defined: the toposort visits shared children more than once. Memoize by node identity.
  • Old code runs after you change the compiler: dlopen returned the library already loaded from that path. Name each .so by a hash of its source.
  • C and interpreter disagree only on overflow tests: clang assumed signed add cannot overflow. Do i32 arithmetic in uint32_t.

Ready to move on when

  • python3 run_tests.py 1 and python3 run_tests.py 2 both pass with the C backend
  • rejected_load_without_after, rejected_store_oob and rejected_store_dtype print REJECTED
  • Interpreter and C backend give the same value on every test file
  • 10+ new tests in tests/week02

Going deeper (optional)

  • Russ Cox, Programming Language Memory Models — Follow-up on how languages expose ordering.
  • John Regehr, A Guide to Undefined Behavior in C and C++, Part 1 — Why generated signed i32 arithmetic needs the uint32_t round-trip.
