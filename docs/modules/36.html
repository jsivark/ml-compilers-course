36Numerics and low precision

Inference cost is dominated by bytes moved, so every frontier serving stack runs fp8, int4 or MX formats. Knowing exactly where precision is lost, and how to recover it, is a top skill in inference and kernel teams.

about 40–60 h · difficulty ●●●●○

After this module you can

  • After this module you can derive and emulate any fp/MX format bit-exactly
  • After this module you can implement GPTQ, AWQ and SmoothQuant and diagnose accuracy loss
  • After this module you can write fused dequant-matmul kernels
  • After this module you can design a precision recipe for a model and defend it with numbers

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    Fabien Sanglard, Floating point visually explained

    Warm-up; then derive bf16, fp16, fp8 E4M3/E5M2 ranges by hand.

  2. Read

    FP8 Formats for Deep Learning (Micikevicius et al.)

    E4M3 vs E5M2, scaling, which tensors get which format.

  3. Read

    OCP Microscaling (MX) Formats v1.0 spec

    Sections 5-6: shared E8M0 block scale, MXFP8/6/4 and MXINT8 element encodings.

  4. Read

    Microscaling Data Formats for Deep Learning

    Empirical results for MX training and inference.

  5. Read

    LLM.int8()

    Outlier features and mixed-precision decomposition.

  6. Read

    SmoothQuant

    Migrating activation outliers into weights; derive the scaling factor alpha.

  7. Read

    GPTQ

    OBQ-style second-order rounding; sections 3-4 incl. the lazy batch updates and Cholesky trick.

  8. Read

    AWQ

    Activation-aware per-channel scaling; compare with GPTQ.

  9. Implement

    FP8 training recipe in Transformer Engine

    Read the FP8 docs and delayed-scaling recipe; run the example on a small model.

  10. Implement

    Bit-exact format emulators

    Write numpy emulators for bf16, fp8 E4M3/E5M2 and MXFP4 (round-to-nearest-even, saturation), tested against torch.float8 dtypes.

  11. Implement

    Quantized matmul kernel

    W4A16 Triton kernel with in-kernel dequantization; add it to your compiler as a dtype.

Build

Format emulators, GPTQ and AWQ implemented from scratch on a ~1B model, and a W4A16 kernel used by your compiler.

Portfolio project: Precision study: how low can a real LLM go?

Take an open 1-8B model and build a systematic study across bf16, fp8 (per-tensor vs. per-channel), MXFP8/MXFP4 and int4 (GPTQ vs. AWQ), measuring perplexity, a downstream task and real throughput with your kernels. Find which layers are sensitive and propose a mixed-precision recipe.

Deliverables

  • repo with emulators, quantizers, kernels and an eval harness
  • README with accuracy-vs-bytes Pareto plot and per-layer sensitivity heatmap
  • a 600–1200 word write-up of findings and the recommended recipe

Rubric

Solid
At least 6 configurations evaluated on 2 metrics with measured speed; reproducible scripts
Exceptional
A mixed-precision recipe that Pareto-dominates uniform int4 or MXFP4, with kernel speedups measured, written up as a blog post others cite

References: OCP MX spec v1.0, GPTQ

If you get stuck

  • Emulator off by one ulp: you truncated instead of round-to-nearest-even, or mishandled subnormals
  • GPTQ blows up: add damping to the Hessian diagonal (the paper uses 1% of the mean)
  • Perplexity numbers don't match papers: same eval context length, dataset split and tokenizer
  • Quantized kernel slow: dequantize in registers after loading packed ints, not into smem

Ready to move on when

  • Emulators bit-match torch.float8_e4m3fn/e5m2 casts on 1e6 random values
  • Your GPTQ 4-bit model is within 0.5 perplexity of the reference implementation on WikiText-2
  • W4A16 kernel is faster than fp16 at batch 1 decode shapes
  • You can explain why E4M3 has no infinity and what that means for scaling
