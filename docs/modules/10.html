Part II · Bridge

10Interpreters

An interpreter is the simplest complete language implementation: scanner, parser, AST, evaluator. Every compiler you build later reuses these front-end pieces, and a tree-walking interpreter is the reference semantics you test compiled code against.

about 30–45 h (14 chapters, about 2-3 h each including code) · difficulty ●●○○○

StepsBuildProjectHelpGo deeper

After this module you can

  • Write a scanner and a recursive-descent parser with precedence levels and panic-mode error recovery.
  • Implement lexical scoping, closures and a resolver pass in a tree-walking interpreter.
  • Explain, with a measured timing, why the clox bytecode VM is faster than the tree-walker.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    Crafting Interpreters ch. 2 A Map of the Territory

    Read for the vocabulary (front end, IR, back end, tree-walk vs bytecode). Skip ch. 3 (Lox spec) on first pass; skim it as reference.

  2. Do

    Crafting Interpreters ch. 4 Scanning

    Port jlox's scanner to Python and print the token stream for a few sample files. Do challenge 4 (C-style /* ... */ block comments, optionally nested).

  3. Read

    Crafting Interpreters ch. 5 Representing Code

    Focus on the grammar notation and the Visitor pattern; in Python, dataclasses plus match statements replace the generated AST classes.

  4. Do

    Crafting Interpreters ch. 6 Parsing Expressions

    Implement recursive descent with one function per precedence level and panic-mode synchronization (section 6.3). Print an S-expression for every parsed expression.

  5. Do

    Crafting Interpreters ch. 7 Evaluating Expressions

    Write the evaluator with runtime type errors. This is your first working calculator REPL.

  6. Do

    Crafting Interpreters ch. 8 Statements and State

    Add statements, globals, assignment and block scopes via an environment chain.

  7. Do

    Crafting Interpreters ch. 9 Control Flow and ch. 10 Functions

    Add if/while/for (for desugars to while), then functions and closures (ch. 10). Ch. 10 adds the native clock() and a recursive fib example; keep it as your benchmark.

  8. Do

    Crafting Interpreters ch. 11 Resolving and Binding

    Your first static pass over the AST: compute the scope distance of each variable use. Classes (ch. 12-13) are optional.

  9. Read

    Crafting Interpreters ch. 14 Chunks of Bytecode

    Start Part III (clox, in C). Read ch. 14 and ch. 15 A Virtual Machine for the chunk format and the stack-based dispatch loop.

  10. Do

    Crafting Interpreters ch. 15-17: VM, Scanning on Demand, Compiling Expressions

    Build the stack VM and the single-pass Pratt compiler in C. At the end of ch. 17 clox evaluates expressions only; functions arrive in ch. 24 Calls and Functions.

  11. Build

    Measure tree-walk vs bytecode

    If you stopped at ch. 17, time both implementations on the same large generated arithmetic expression evaluated many times. If you reached ch. 24, time fib(30) in both. Record the numbers for the write-up.

Build

A Python tree-walking interpreter for a Lox subset (expressions, variables, blocks, if/while/for, functions with closures) with a resolver pass, plus a C bytecode VM that evaluates arithmetic expressions through a Pratt compiler; include a test directory of .lox programs with expected outputs and a runner script.

Portfolio project: Bytecode VM for your Lox subset with a measured speedup

Skill project

Extend your tree-walking interpreter with a compiler to a stack-based bytecode and a dispatch-loop VM (in Python first, optionally C). Use the tree-walker as an oracle: a fuzzer generates random programs and asserts both produce identical output. Measure where the speedup comes from (dispatch, environment lookups vs local slots, constant folding at compile time).

Deliverables

  • repo with scanner, parser, tree-walker, bytecode compiler, VM, and a differential fuzzer
  • README with a benchmark table (fib(25), loops, string concat) for tree-walk vs VM, plus a disassembler output example
  • a 600–1200 word write-up explaining the bytecode design, local-slot resolution, and what profiling showed about dispatch overhead

Rubric

Solid
VM passes every tree-walker test plus 1,000 fuzzed programs with zero divergences; at least 3x faster than the tree-walker on fib(25) in the same language.
Exceptional
C VM with computed-goto dispatch, superinstructions justified by an opcode-pair frequency profile, 20x+ speedup, and a fuzzer bug found and documented.

References: Crafting Interpreters ch. 15 A Virtual Machine

Help

If you get stuck

  • Left recursion makes recursive descent call itself forever: rewrite the rule as a loop (section 6.2 Recursive Descent Parsing).
  • Closures capturing the wrong variable means names are being resolved dynamically; ch. 11 Resolving and Binding fixes exactly this bug.
  • Precedence bugs: print the S-expression of every parsed test case before evaluating it.
  • Skip full Lox parity (classes, inheritance) until expressions, statements, functions and closures pass your tests.

Ready to move on when

  • Your parser reports an error on 'print (1 + ;' and continues parsing the next statement
  • Closures work: a makeCounter() function returns counters that increment independently
  • The resolver reports "Can't read local variable in its own initializer." for 'var a = a;' in a local scope
  • You have a timing table comparing your Python tree-walker and C clox on the same input
Reference implementations (4)

Make a real attempt first. When you are stuck, or after you finish, compare your work with these.

  • jlox reference source (Java) (ch. 4-11 tree-walker and resolver)
    Robert Nystrom's finished tree-walking interpreter: Scanner, Parser, Interpreter, Resolver and Environment classes to diff against your Python port.
  • clox reference source (C) (ch. 14-17 bytecode VM and Pratt compiler)
    The complete clox VM, compiler and scanner; compare chunk.c, vm.c and compiler.c with yours chapter by chapter.
  • Official challenge answers (ch. 4 challenge 4 and other chapter challenges)
    The author's answers to the end-of-chapter challenges, including the block-comment scanner challenge.
  • Crafting Interpreters test suite (build: test directory and runner)
    Hundreds of .lox programs with expected output and error annotations, ready to drive your own test runner.

Talks, papers, code and writing (16)

Talks

  • A deep dive into dispatching techniques (slides) · Jonathan Mueller, think-cell
    Slides walking a bytecode VM from switch dispatch through computed goto to tail-call threading, with generated assembly for each; focus on the tail-call section.

Papers

  • The Implementation of Lua 5.0 · Roberto Ierusalimschy, Luiz Henrique de Figueiredo, Waldemar Celes
    Explains Lua's switch from a stack VM to a register VM and its closure (upvalue) design; read sections 5-7.
  • PEP 659: Specializing Adaptive Interpreter · Mark Shannon
    Explains how CPython 3.11 rewrites bytecode in place with quickened, type-specialized instructions; focus on the specialization and deoptimization sections.

Books

  • Writing An Interpreter In Go · Thorsten Ball
    A second tree-walker built test-first with a Pratt parser; its sequel adds a bytecode compiler, a parallel route to clox.
  • A Python Interpreter Written in Python (500 Lines or Less) · Allison Kaptur
    Builds Byterun, a stack VM that runs real CPython bytecode in about 500 lines; focus on the frame and block-stack sections to compare with clox.

Blogs and articles

  • Simple but Powerful Pratt Parsing · Alex Kladov (matklad)
    A compact Rust Pratt parser built around binding powers; read the prefix/postfix/ternary sections to see how one loop handles all operators.
  • Pratt Parsers: Expression Parsing Made Easy · Robert Nystrom
    The original explanation of the parselet design clox uses; focus on how precedence is passed into parseExpression.
  • Computed goto for efficient dispatch tables · Eli Bendersky
    Measures switch dispatch vs computed goto in a toy VM; apply the trick to clox and time it.
  • (How to Write a (Lisp) Interpreter (in Python)) · Peter Norvig
    A full Scheme interpreter in about 100 lines of Python; a useful contrast in minimalism with jlox.
  • Max Bernstein's blog · Max Bernstein
    Posts on interpreters, inline caching and JITs from a CPython/Cinder engineer; start with the interpreter and inline caching posts.
  • Performance of the Python 3.14 tail-call interpreter · Nelson Elhage
    A 2025 benchmarking investigation showing the headline tail-call dispatch speedup was mostly a Clang 19 regression; read it for how to measure interpreter dispatch changes honestly.
  • Which Parsing Approach? · Laurence Tratt
    A long, opinionated comparison of recursive descent, LR, PEG and others; read it to understand what hand-written Pratt parsers trade away (silent ambiguity resolution).
  • Flattening ASTs (and Other Compiler Data Structures) · Adrian Sampson
    Shows with benchmarks how storing an AST in a flat array with integer indices speeds up a tree-walking interpreter; read the measurements and the arena discussion.

Code to read

  • wren · Robert Nystrom and contributors
    A production-quality descendant of clox's design; read src/vm/wren_vm.c to see NaN boxing and fibers in a real VM.

More reading

  • Crafting Interpreters ch. 30 Optimization — Profiling-driven changes to clox: faster hash table probing (30.2) and NaN boxing (30.3).
  • Build Your Own Lisp — Alternative C-based interpreter if you want more C practice.
