10Interpreters

An interpreter is the simplest complete language implementation: scanner, parser, AST, evaluator. Every compiler you build later reuses these front-end pieces, and a tree-walking interpreter is the reference semantics you test compiled code against.

about 30–45 h · difficulty ●●○○○

After this module you can

  • After this module you can write a scanner and recursive-descent parser with precedence climbing and error recovery for a small language.
  • After this module you can implement lexical scoping, closures and a resolver pass in a tree-walking interpreter.
  • After this module you can use an interpreter as a reference oracle to differentially test a compiler.
  • After this module you can explain the cost model of tree-walking vs bytecode interpretation.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    Crafting Interpreters ch. 2 A Map of the Territory

    Read for the vocabulary (front end, IR, back end, tree-walk vs bytecode). Skip ch. 3 (Lox spec) on first pass; skim it as reference.

  2. Do

    Crafting Interpreters ch. 4 Scanning

    Port jlox's scanner to Python (not Java) and produce a token stream for sample files. Do challenge 1.

  3. Read

    Crafting Interpreters ch. 5 Representing Code

    Focus on the grammar notation and the Visitor pattern; in Python, dataclasses plus match statements replace the generated AST classes.

  4. Do

    Crafting Interpreters ch. 6 Parsing Expressions

    Implement recursive descent with precedence levels and error synchronization. Produce a parser that prints an S-expression for any expression.

  5. Do

    Crafting Interpreters ch. 7 Evaluating Expressions

    Write the evaluator with runtime type errors. This is your first working calculator REPL.

  6. Do

    Crafting Interpreters ch. 8 Statements and State

    Add statements, globals, assignment and block scopes via an environment chain.

  7. Do

    Crafting Interpreters ch. 9 Control Flow and ch. 10 Functions

    Add if/while/for (desugared to while) and then functions with closures (ch. 10). Write a fib benchmark you will reuse.

  8. Do

    Crafting Interpreters ch. 11 Resolving and Binding

    Your first static pass over the AST: compute scope distances. This is the template for every later analysis pass. Classes (ch. 12-13) are optional.

  9. Read

    Crafting Interpreters ch. 14 Chunks of Bytecode

    Start Part III (clox, in C). Read ch. 14 and 15 A Virtual Machine to see why bytecode beats tree-walking.

  10. Do

    Crafting Interpreters ch. 15-17: VM, Scanning on Demand, Compiling Expressions

    Build the stack VM and the Pratt-parser single-pass compiler in C. Stop after ch. 17 or continue to ch. 24 Calls and Functions if time allows.

  11. Build

    Measure tree-walk vs bytecode

    Time fib(30) in your Python jlox port vs your C clox; record numbers for the module write-up.

Build

A Python tree-walking interpreter for a Lox subset (expressions, variables, blocks, if/while/for, functions with closures) with a resolver pass, plus a C bytecode VM that evaluates arithmetic expressions through a Pratt compiler; include a test directory of .lox programs with expected outputs and a runner script.

Portfolio project: Bytecode VM for your Lox subset with a measured speedup

Extend your tree-walking interpreter with a compiler to a stack-based bytecode and a dispatch-loop VM (in Python first, optionally C). Use the tree-walker as an oracle: a fuzzer generates random programs and asserts both produce identical output. Measure where the speedup comes from (dispatch, environment lookups vs local slots, constant folding at compile time).

Deliverables

  • repo with scanner, parser, tree-walker, bytecode compiler, VM, and a differential fuzzer
  • README with a benchmark table (fib(25), loops, string concat) for tree-walk vs VM, plus a disassembler output example
  • a 600–1200 word write-up explaining the bytecode design, local-slot resolution, and what profiling showed about dispatch overhead

Rubric

Solid
VM passes all interpreter tests plus 1,000 fuzzed programs with zero divergences; at least 3x faster than tree-walk on fib(25).
Exceptional
C VM with computed-goto dispatch, superinstructions justified by an opcode-pair frequency profile, 20x+ speedup, and a fuzzer bug found and documented.

References: Crafting Interpreters ch. 14 Chunks of Bytecode onward (clox)

If you get stuck

  • Left recursion in a grammar makes recursive descent loop forever: rewrite as iteration (ch. 6 'Ambiguity and the Parsing Game').
  • Closures capturing the wrong variable usually means you resolve names dynamically; implement the resolver from ch. 11 'Resolving and Binding'.
  • Runaway precedence bugs: print the S-expression of every parsed test case before evaluating.
  • Python recursion limit hits on deep fib benchmarks: raise sys.setrecursionlimit only for tests, and note it as a reason bytecode VMs exist.
  • Don't chase full Lox parity; get expressions, statements, functions and closures solid first.

Ready to move on when

  • Your parser reports a useful error and recovers on 'print (1 + ;' instead of crashing
  • Closures work: a counter-maker function returns independent counters
  • The resolver rejects 'var a = a;' in a local scope
  • You can explain in two sentences why the clox VM is faster than the tree-walker and back it with a measured timing

Going deeper (optional)

  • Build Your Own Lisp — Alternative C-based interpreter if you want more C practice.
