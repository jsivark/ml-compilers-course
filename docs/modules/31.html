31Final project: results and write-up

Writing it up as a short paper forces you to state what you claim and back it with numbers.

about 30–45 h · difficulty ●●●●○

StepsBuildProjectHelpGo deeper

After this module you can

  • Write a 4-page report whose headline claim is backed by a reproducible number.
  • Package code so a stranger reproduces your results from the README.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    Simon Peyton Jones, How to Write a Great Research Paper

    Use its advice: state one key idea, list contributions explicitly, show examples before generality.

  2. Implement

    Final benchmark run

    Fresh run of the harness on clean hardware; tables and plots.

  3. Implement

    Write the 4-page report

    Problem, method, results, ablations, negative results, limitations.

  4. Implement

    Clean up code and README

    Reproduction instructions for the harness.

  5. Test

    End-to-end demo

    README Week 6 milestones: MNIST MLP to at least 97% test accuracy, and stories15M producing the same tokens as llama2.c run.c.

  6. Read

    Simon Peyton Jones, How to Give a Great Research Talk

    One key idea; examples before generality.

  7. Implement

    Record a 15-minute talk with demo and publish

    Slides, live demo, link from README; share publicly and collect feedback.

Build

Code, a reproducible harness, a 4-page report and a 15-minute recorded talk with demo.

Portfolio project: Capstone phase 3: public technical report, talk and demo

Capstone

Publish a 4-page report (PDF or blog post), a 15-minute recorded talk with a demo (MNIST training, stories15M generation, and the project result), and a reproducible repo. Post it publicly and record the feedback.

Deliverables

  • public repo with one-command reproduction and a results table matching the report
  • 4-page report: problem, method, results, ablations, negative results, limitations, related work
  • 15-minute recorded talk with slides and demo, linked from the README
  • a short post (blog, X, HN, tinygrad/GPU MODE Discord) with the headline figure, and notes on feedback received

Rubric

Solid
Report is self-contained and every number reproduces; talk fits 15 minutes with a working demo.
Exceptional
Someone else reproduces your headline number from the README and says so publicly, or the report is submitted to a workshop.

References: Simon Peyton Jones, How to Write a Great Research Paper, Simon Peyton Jones, How to Give a Great Research Talk

Help

If you get stuck

  • Report lists what you did instead of what you found: lead with the claim and the headline number.
  • Plots without baselines or error bars: every chart needs a comparison and variance.
  • Talk too detailed: one idea, one key figure, one demo; backup slides for the rest.
  • Reproduction fails on a fresh machine: test the README on a clean container or cloud VM before publishing.

Ready to move on when

  • 4-page report with results and negative results
  • Harness reproduces the numbers
  • Compiler trains MNIST to >=97% and stories15M matches run.c tokens
  • 15-minute talk with working demo recorded and published
Reference implementations (4)

Make a real attempt first. When you are stuck, or after you finish, compare your work with these.

  • tinygrad beautiful_mnist.py (pinned) (End-to-end demo: MNIST)
    tinygrad MNIST training script reaching 98%+; compare model, optimizer and JIT setup with your MNIST demo.
  • llama2.c run.c (End-to-end demo: stories15M)
    The reference generator your stories15M tokens must match; also a model README with one-command reproduction.
  • tinygrad llama.py (pinned) (End-to-end demo: stories15M)
    How tinygrad loads LLaMA weights and samples; a compiler-side reference for the generation demo.

Go deeper (optional)

Talks, papers, code and writing (11)

Lectures

  • You and Your Research · Richard Hamming
    The section on selling your work explains why presentation matters as much as results.
  • How to write a good paper (slides) · Gernot Heiser
    Systems-focused slides arguing evaluation is the core of the paper; focus on the evaluation and honesty-about-limitations sections.

Papers

  • FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness · Tri Dao et al.
    A model systems paper: one key idea, an IO-complexity argument, then benchmarks and ablations; mirror its structure in your 4 pages.
  • TVM: An Automated End-to-End Optimizing Compiler for Deep Learning · Tianqi Chen et al.
    Study how the evaluation compares against vendor libraries across hardware for your related-work and results sections.
  • Flex Attention: A Programming Model for Generating Optimized Attention Kernels · Juechu Dong, Boyuan Feng, Driss Guessous, Yanbo Liang, Horace He
    A short compiler paper with clear claims against hand-written kernels; a good length and style reference.
  • How (and How Not) to Write a Good Systems Paper · Roy Levin and David D. Redell (1983)
    The classic SOSP reviewer checklist; run your write-up against its questions on the new idea, implementation and comparison to prior techniques.

Blogs and articles

  • Accelerating Generative AI with PyTorch II: GPT, Fast · PyTorch team (Horace He et al.)
    A post that leads with a headline number and a single chart per step; the format to use for your public post.
  • Systems Benchmarking Crimes · Gernot Heiser
    Run your final tables and plots past this list before publishing.
  • FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling · Tri Dao
    An exemplary public write-up of a kernel project; copy how it states the hardware bottleneck first, then the schedule, then the measured results.
  • ThunderKittens Now on Blackwells! · Benjamin Spector, Aaryan Singhal, Dan Fu, Chris Re (Hazy Research)
    A short, readable results post with cuBLAS comparisons; use it as a model for presenting your final numbers to a general systems audience.
  • One Kernel for All Your GPUs · Hazy Research (Stanford)
    Another worked results post from a research lab; note how plots and baselines are chosen to support one main claim.
Stretch project

Submit the report as a 4-page workshop paper (for example an MLSys or NeurIPS ML-for-systems workshop) with an artifact that an independent person reproduces within 10% of your headline number. Record the review feedback and the reproduction in the README.
