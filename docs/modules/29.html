Part III · The Course · 10-411 week 12

29Final project: choose, baseline, harness

Projects fail from vague goals and missing measurements. Lock in one metric and a reproducible harness before optimizing anything.

about 20–35 h · difficulty ●●●●○

StepsBuildProjectHelpGo deeper

After this module you can

  • State the project as a falsifiable claim with one primary metric.
  • Run a benchmark harness that pins versions and records hardware.
  • Measure the strongest public baseline (PyTorch, cuBLAS, llm.c, tinygrad) for your target.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: 'Weeks 12-End: Student Projects'

    The 10-411 syllabus heading reads 'Use your compiler to implement a paper, port it to strange hardware, mostly anything'; the final project is 25% of the grade (weeks 11-14).

  2. Read

    Idea A, kernel search: tinygrad beam_search

    beam_search() in tinygrad/codegen/opt/search.py tries kernel optimizations and keeps the fastest timed candidates. Project idea: replace your hand heuristics with the same kind of search over your schedule space. Related: Ansor (arXiv 2006.06762).

  3. Read

    Idea B, Hopper/FA3-style attention: FlashAttention-3 §3

    Section 3.1 covers producer-consumer warp specialization and pingpong scheduling. Only pick this idea if you have an H100.

  4. Read

    Idea C, e-graph rewriting: egg paper sections 1-4

    Section 2 defines e-graphs and equality saturation, section 4.3 covers extraction. Project idea: replace your greedy rewriter with equality saturation and compare kernel cost.

  5. Read

    Idea D, training a small LLM: llm.c

    GPT-2 (124M) training in C/CUDA. Project idea: use it as the target workload and baseline for your compiler.

  6. Implement

    Choose and write the scope

    Write one sentence of the form 'X is N% faster/smaller than Y on Z', the metric, the baseline, and what is out of scope.

  7. Implement

    Baseline

    Get the reference (PyTorch, llm.c, cuBLAS, current compiler) running and record numbers.

  8. Implement

    Benchmark harness

    One script runs baseline and yours, checks outputs match, records the median of N runs plus GPU model, driver and library versions, and appends to a CSV.

  9. Measure

    First full harness run

    Run the harness end to end and commit the baseline numbers.

  10. Implement

    Write a one-page proposal and get one reviewer

    Claim, primary metric, baseline, kill criteria; post it for feedback before coding.

Build

A chosen project with a written scope, a running baseline and a reproducible harness.

Portfolio project: Capstone phase 1: proposal, baseline and public harness

Capstone

Write a one-page proposal (problem, claim, primary metric, baseline, risks, stretch goal) and get feedback from at least one other person (forum, Discord, a peer). Publish the harness repo with baseline numbers before you write any optimization code. The capstone can extend kiln or stand alone. A research track is also available: see Module 39.

Deliverables

  • public repo with harness, pinned environment and baseline results
  • one-page proposal in the repo (claim, metric, baseline, timeline, kill criteria)
  • a baseline table with mean and variance over 3+ runs, plus the roofline bound for the target
  • written feedback from one reviewer and your response

Rubric

Solid
Claim is falsifiable; baseline is the strongest public implementation; anyone can reproduce baseline numbers in under 30 minutes.
Exceptional
Harness runs in CI; the proposal states the roofline ceiling for the target and the expected gap before any optimization code exists.

References: Simon Peyton Jones, How to Write a Great Research Paper, How to Scale Your Model: All About Rooflines

Help

If you get stuck

  • Scope too big: if you cannot state the result as 'X is N% faster/smaller than Y on Z', narrow it.
  • Weak baseline: comparing against your own unoptimized code proves nothing; use the best public implementation.
  • Harness not reproducible: pin versions, record GPU clocks and driver, run 3+ trials and report variance.
  • Picking a project nobody can evaluate: choose a number (speed, memory, bugs found), not 'clean design'.

Ready to move on when

  • Scope document with goal, metric, baseline
  • Baseline runs and numbers are recorded
  • Harness checks correctness and timing reproducibly
Reference implementations (5)

Make a real attempt first. When you are stuck, or after you finish, compare your work with these.

  • tinygrad search.py (pinned) (Idea A, kernel search)
    Full source of beam_search, including candidate generation, timing with warmup and caching of results; compare your search loop against it.
  • tinygrad process_replay.py (pinned) (Benchmark harness)
    How tinygrad diffs generated kernels between HEAD and master in CI; a model for the correctness half of your harness.
  • egg (Rust e-graph library) (Idea C, e-graph rewriting)
    Reference implementation of the egg paper with tests and examples of rewrite rules and cost-based extraction.
  • flash-attention-minimal (Idea B, attention)
    About 100 lines of CUDA forward FlashAttention; a readable baseline before attempting the FA3 idea.
  • llama2.c (Baseline)
    run.c is the token-exact reference for the stories15M milestone and a small baseline workload.

Go deeper (optional)

Talks, papers, code and writing (15)

Lectures

  • You and Your Research · Richard Hamming
    Hamming on choosing important problems; read it before picking between ideas A-D.

Papers

  • TVM: An Automated End-to-End Optimizing Compiler for Deep Learning · Tianqi Chen et al.
    Read section 5 (automated optimization) to see how a search space plus a cost model is framed, which shapes a good project scope.
  • Learning to Optimize Tensor Programs · Tianqi Chen et al.
    AutoTVM: learned cost models for schedule search; the evaluation section shows how to present search results against vendor baselines.
  • Statistically Rigorous Java Performance Evaluation · Andy Georges, Dries Buytaert, Lieven Eeckhout (OOPSLA 2007)
    Shows how best-of-N and mean-only reporting mislead; read the confidence-interval and ANOVA sections and apply them to your baseline timing runs.
  • Producing Wrong Data Without Doing Anything Obviously Wrong! (ASPLOS 2009) · Todd Mytkowicz, Amer Diwan, Matthias Hauswirth, Peter F. Sweeney
    Measurement bias from link order and environment size can flip conclusions; read it before trusting a single setup and plan to randomize your harness setup.

Blogs and articles

  • Systems Benchmarking Crimes · Gernot Heiser
    A checklist of benchmarking mistakes (selective subsets, no variance, wrong baseline); check your proposal against it.
  • How to Scale Your Model · Austin, Douglas, et al. (Google DeepMind)
    Chapters on transformer math and inference let you compute the roofline bound for an LLM-scale project target.
  • Modal GPU Glossary · Modal
    Short linked definitions of GPU hardware and software terms; use it to write precise proposal language about SMs, tensor cores and memory.
  • GEMM Performance Measurement Methodology Guidelines · NVIDIA CUTLASS docs
    NVIDIA's own rules for timing GEMMs (clock monitoring, cold caches via rotated buffers, no gaps between launches); use it as the checklist for your project's baseline harness.
  • How we (try to) benchmark GPU kernels accurately · Jan.ai
    Practitioner write-up on L2 flushing, CUDA events and warmup; copy its L2-flush approach into your harness before recording any baseline.
  • CUDA Performance Hot VS Cold Measurement · Lei Mao
    A small C++ harness that flushes L2 with cudaMemsetAsync before each timed launch; copy its structure for the cold-cache mode of your benchmark.

Code to read

  • modded-nanogpt (nanoGPT speedrun) · Keller Jordan et al.
    A record log where each entry is one measured change to time-to-loss; read the record history as a model of a scoped, measurable claim.

Problem sets

  • KernelBench · Stanford Scaling Intelligence Lab
    250 PyTorch reference ops with a correctness and speedup harness; a ready-made baseline suite and a design to copy for your harness.
  • GPU MODE reference kernels · GPU MODE
    Problem definitions and reference code for the GPU MODE leaderboards; pick one as a project with a public ranking as the metric.

More reading

  • tinygrad-notes: BEAM search — How tinygrad searches kernel optimizations.
Stretch project

Turn Idea A into a learned search: train a small cost model (gradient-boosted trees or an MLP over kernel features) on timings from your beam search, and show it reaches within 5% of full-beam kernel speed on 20+ KernelBench level-1 ops while timing at least 5x fewer candidates. Publish the dataset of (kernel, features, time) so others can reproduce.
