16Performance engineering

An ML compiler is only as good as the code it generates. MIT 6.172 teaches you to reason about work, caches, vectorization and measurement; Aalto PPC makes you optimize one real kernel step by step on CPU, which is what kernel codegen must reproduce automatically.

about 40–60 h · difficulty ●●●●○

After this module you can

  • After this module you can reason with roofline models and compute arithmetic intensity for real kernels.
  • After this module you can optimize a CPU GEMM with blocking, packing, SIMD and multithreading to a large fraction of peak.
  • After this module you can profile with perf/Instruments, read flame graphs and hardware counters, and attribute time correctly.
  • After this module you can run statistically sound benchmarks (warmup, variance, pinned frequency).

Steps

Work through these in order. Each step points at one specific unit.

  1. Watch

    MIT 6.172 Lecture 1: Introduction and Matrix Multiplication

    The famous 50000x matmul speedup ladder: loop order, compiler flags, parallel loops, tiling, vectorization.

  2. Watch

    MIT 6.172 Lecture 2: Bentley Rules for Optimizing Work

    Catalog of work-reducing transforms; many are compiler passes.

  3. Watch

    MIT 6.172 Lecture 4: Assembly Language and Computer Architecture

    Pipelines, vector units; connects to your Module 11 codegen.

  4. Watch

    MIT 6.172 Lecture 5: C to Assembly

    How compilers lower C to LLVM IR and assembly.

  5. Watch

    MIT 6.172 Lecture 9: What Compilers Can and Cannot Do

    Essential: aliasing, inlining, vectorization limits.

  6. Do

    MIT 6.172 HW1: Basic Tools, C Primer and HW3: Vectorization

    HW1 covers tooling (perf, sanitizers, valgrind); HW3 has you read clang vectorization reports and coax loops into SIMD. Skip the Cilk-specific HW4 unless you install OpenCilk.

  7. Read

    Aalto PPC Chapter 2: Case study, V0-V7 (+ Asm pages)

    Read the full case study: baseline, linear reading, instruction-level parallelism, vectors, reuse, prefetch, more registers.

  8. Do

    Aalto PPC exercises CP1, CP2a, CP2b, CP2c, CP3a

    Register for the open course; CP1 baseline, CP2a instruction-level parallelism, CP2b multithreading, CP2c vectorization, CP3a fast solution. Submit to the grader and record runtime per version, mirroring V0-V7 from Chapter 2.

  9. Do

    Aalto PPC exercise IS4 or MF1 (optional second kernel)

    Pick one more to practice on a different access pattern.

  10. Read

    Algorithmica HPC: SIMD Parallelism and Matrix Multiplication

    Read the matmul chapter: micro-kernel, blocking, and how BLIS-style kernels reach peak.

  11. Build

    Hand-optimize a CPU matmul to >50% of peak

    In C with intrinsics: naive -> transposed -> blocked -> micro-kernel -> OpenMP; plot GFLOP/s per step.

Build

A benchmarked CPU SGEMM in C (callable from your Module 15 library via ctypes) with a writeup plotting GFLOP/s across 6 optimization stages against theoretical peak, plus perf counter evidence (cache misses, IPC) for each stage.

Portfolio project: CPU SGEMM reaching a stated fraction of peak, with a roofline report

Write a single-precision GEMM in C from naive loops to a packed, register-blocked, SIMD (AVX2/AVX-512 or NEON), multithreaded kernel. Document each optimization step with measured GFLOP/s and hardware counters, place each version on a roofline for your machine, and compare to OpenBLAS/Accelerate.

Deliverables

  • repo with each optimization step as a separate tagged version and a reproducible benchmark harness
  • README with GFLOP/s vs matrix size plots, a roofline chart, and cache-miss counters per version
  • a 600–1200 word write-up explaining micro-kernel design, packing, and why each step helped

Rubric

Solid
Single-thread kernel reaches 50%+ of theoretical peak on large sizes; all versions verified against a reference.
Exceptional
80%+ of peak and within 10–20% of OpenBLAS/Accelerate, with a tuned micro-kernel justified by register/latency arithmetic and multithreaded scaling analysis.

References: how-to-optimize-gemm, Brendan Gregg: Flame Graphs

If you get stuck

  • Noisy timings: warm up, repeat, report median and spread; disable turbo or pin cores where possible.
  • The compiler deleted your benchmark: consume results or use a DoNotOptimize-style barrier.
  • Check vectorization with compiler reports (-Rpass=loop-vectorize / -fopt-info-vec) rather than guessing.
  • Cache blocking sizes depend on your actual L1/L2; measure, don't copy numbers from blogs.
  • Compute your machine's theoretical peak FLOPS first so you know what 'fast' means.

Ready to move on when

  • You can compute your CPU's theoretical peak FLOP/s from cores, frequency, SIMD width and FMA units
  • Your final matmul is within 2x of OpenBLAS/numpy at 2048x2048
  • You can explain from perf counters why loop order i-k-j beats i-j-k
  • Aalto CP3a passes the grader at the benchmark time limit
