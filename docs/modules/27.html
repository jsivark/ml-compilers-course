27Multiple GPUs, sharding

Sharding is a type on buffers and collectives are just ops your compiler inserts. Data and tensor parallelism fall out of propagating that annotation.

about 30–45 h · difficulty ●●●●○

After this module you can

  • After this module you can annotate tensors with shardings and propagate them through a graph.
  • After this module you can insert collectives (all-reduce, all-gather, reduce-scatter) automatically.
  • After this module you can implement data parallel and tensor parallel (Megatron-style) layers.
  • After this module you can model communication cost and overlap it with compute.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    Scaling Book: Sharded Matrices and How to Multiply Them

    The sharding notation and the four matmul cases with their required collectives.

  2. Read

    Scaling Book: How to Parallelize a Transformer for Training

    Data, FSDP, tensor parallelism; which collective each needs.

  3. Implement

    shard annotation and propagation

    Add shard=axis to buffers; propagate through elementwise, reduce and movement ops.

  4. Read

    tinygrad multi.py: alu_multi, reduce_multi, reshape_multi

    How sharding propagates per op; reduce_multi (107) is where all-reduce appears.

  5. Implement

    Collective insertion pass

    Insert all-reduce after reductions over a sharded axis and all-gather when an unsharded consumer needs the full tensor.

  6. Read

    NCCL user guide: Collective Operations

    AllReduce, AllGather, ReduceScatter semantics; call via ctypes.

  7. Implement

    Data-parallel MNIST on 2+ GPUs

    Shard the batch, all-reduce gradients, match single-GPU loss curve.

  8. Read

    Megatron-LM §3 (tensor model parallelism)

    Column- then row-parallel MLP with one all-reduce.

  9. Implement

    Tensor-parallel matmul

    Shard weights column/row-wise; check vs single GPU.

  10. Watch

    LLM Training Puzzles

    Do the puzzles to check your understanding of comms schedules.

  11. Measure

    Scaling efficiency

    Report speedup on 2 GPUs vs 1 and comms time fraction.

Build

A shard annotation, a collective insertion pass, data-parallel MNIST and a tensor-parallel matmul.

Portfolio project: Sharding planner with a communication cost model

Given a model graph and a device count, have your compiler search over shardings (data, tensor, mixed) using a cost model of compute and collective bytes, then run the chosen plan and compare predicted vs measured step time. Include overlap of communication with compute as an optional optimization.

Deliverables

  • repo with the planner, cost model and a multi-process runner (multi-GPU or simulated)
  • README with predicted vs measured step time per plan, scaling efficiency from 1 to N devices
  • measured collective bandwidth (nccl-tests or your own) feeding the cost model
  • a 600–1200 word write-up on when tensor parallel beats data parallel for your models

Rubric

Solid
Planner picks the measured-best plan on 2+ models; scaling efficiency reported honestly; results match single-device outputs.
Exceptional
Cost model within 15% of measured; comm/compute overlap gives a measured speedup; plan search scales to a transformer block with mixed DP+TP.

References: Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism, nccl-tests

If you get stuck

  • Sharded result is off by a factor of N: you all-reduced a value that was already replicated, or averaged instead of summed.
  • Hangs: ranks issue collectives in different orders. Make collective order deterministic from the graph.
  • No speedup: communication dominates. Measure bus bandwidth with nccl-tests and compare to your step time.
  • Only 1 GPU available: simulate ranks with processes on CPU (gloo-style) so the pass is still testable.

Ready to move on when

  • Data-parallel MNIST on >= 2 GPUs with compiler-inserted all-reduce
  • Tensor-parallel matmul matches single GPU
  • Scaling numbers reported
  • All earlier tests pass
