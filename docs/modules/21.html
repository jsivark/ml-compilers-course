21Rangeify, reduce, materialization

Rangeify lowers shaped ops into scalar code over explicit ranges and decides what to materialize; that is the scheduler at the heart of every ML compiler. Fusion vs staging is where performance is won or lost.

about 30–45 h · difficulty ●●●●○

After this module you can

  • After this module you can lower tensor-level expand/reduce ops to scalar loops (rangeify).
  • After this module you can decide when to fuse producers into consumers and when to materialize a buffer.
  • After this module you can quantify the memory-traffic cost of a fusion decision.
  • After this module you can debug scheduling bugs by inspecting the lowered loop structure.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: Week 4

    REDUCE, STAGE, EXPAND, and 'rangeify removes shapes from all ops'.

  2. Implement

    expand, reduce, rank-1 ALU: types and shapes

    Shape rules for broadcast and reduce of the last n axes. Pass rejected_shape_mismatch, elementwise_rank1 in the interpreter.

  3. Read

    Halide paper §1-§3 (algorithm vs schedule)

    Focus on §3 'scheduling' (compute_at / store_at, the fusion-vs-recompute trade-off); skip the autotuner.

  4. Read

    tinygrad-notes: operator fusion

    How tinygrad decides kernel boundaries.

  5. Implement

    Rangeify pass

    Rewrite each shaped node into a scalar node indexed by fresh ranges (elementwise shares its consumer's ranges; reduce opens new ranges and an accumulator). Pass dot_product, reduce_max, reduce_expand, mismatch_reduce.

  6. Read

    tinygrad run_rangeify and pm_apply_rangeify

    Read run_rangeify and convert_reduce_to_reduce_with_ranges (line 104) after your first version.

  7. Implement

    Materialization decision

    Fuse elementwise chains into one loop; insert a staged temp buffer only when a value is needed with different ranges (e.g. reduce input read twice).

  8. Read

    tinygrad stage / _limit_bufs

    See how STAGE introduces a buffer, and remove_bufferize (line 46) for un-materializing.

  9. Test

    Inspect generated C for reduce(mul(a,b))

    Confirm one loop, no temp buffer, accumulator in a register.

  10. Measure

    Count kernels/buffers per test

    Print loops and temp buffers per program; make a table to keep as a regression check.

  11. Test

    10 own tests

    E.g. softmax-like reduce reused twice (must stage), expand of a reduce, max-reduce of negatives (init to INT_MIN, not 0).

Build

A rangeify pass that lowers expand/reduce/rank-1 ALU to scalar loops and decides fusion vs staging.

Portfolio project: Fusion explorer with a cost model and ablation study

Expose every fuse-vs-materialize decision as a knob, then build a tool that enumerates (or samples) fusion plans for a model graph, estimates bytes moved and FLOPs with your cost model, and measures the real runtime. Show how well your cost model ranks plans and where it is wrong.

Deliverables

  • repo with a plan enumerator, a cost model and a runner
  • README with a scatter plot predicted vs measured time (Spearman rank correlation reported) on 3+ graphs (MLP, softmax, layernorm)
  • a graph view of the chosen plan vs the naive one, with buffer sizes annotated
  • a 600–1200 word write-up on where fusion hurts and how your heuristic handles it

Rubric

Solid
Chosen plan beats no-fusion and fuse-everything on all 3 graphs; cost model rank correlation above 0.7.
Exceptional
Matches or beats tinygrad's scheduler on the same graphs on your machine; cost model refined with measured cache effects; finds a counterintuitive case (fusion slows things down) and explains it with counters.

References: TVM: An Automated End-to-End Optimizing Compiler for Deep Learning, How to Scale Your Model: All About Rooflines

If you get stuck

  • Fusing a reduce into its consumer recomputes the reduce per output element: materialize when a reduce result is used by more than one loop iteration.
  • Wrong results after fusion: a range was shared by two ops that need independent loops. Give each reduce its own range variables.
  • Exponential blow-up when fusing a node with many consumers: duplicating compute is not free, cap it with a cost model.
  • Accumulator not initialized per output: the reduce init must be inside the outer loops, not hoisted above them.

Ready to move on when

  • python3 run_tests.py 4 (and 1-3) pass
