21Rangeify, reduce, materialization

Rangeify lowers shaped ops to scalar code over explicit ranges and decides which values get a buffer. Fuse-or-stage is the scheduling decision every ML compiler makes.

about 25-40 h · difficulty ●●●●○

StepsBuildProjectHelpGo deeper

After this module you can

  • Lower expand, reduce and rank-1 ALU to scalar loops over explicit ranges.
  • Decide per value whether to fuse it into its consumer or stage it in a temp buffer, and show the decision in the generated C.
  • Count loops and temp buffers per program and keep the counts as a regression check.

Steps

Work through these in order. Each step points at one specific unit.

  1. Read

    10-411 syllabus: Week 4

    REDUCE (axis count / op), STAGE (temp buffer), EXPAND, and 'Rangeify removes shapes from all ops'.

  2. Implement

    expand, reduce, rank-1 ALU: types and shapes

    Shape rules for expand (scalar to (n,)) and reduce of the last pop axes. REJECT rejected_shape_mismatch; pass elementwise_rank1 in the interpreter first.

  3. Read

    Halide (PLDI 2013) sections 1-3

    Section 3, 'Scheduling Image Processing Pipelines': 3.1 walks a two-stage blur through inline, root and tiled schedules; 3.2 models a schedule as where each stage is computed and where it is stored. Skip section 5 (autotuning).

  4. Read

    tinygrad-notes: Short note on operator fusion

    a+4+3 becomes one kernel; calling realize() on the intermediate forces two. Written against an older tinygrad.

  5. Implement

    Rangeify pass

    Rewrite each shaped node into a scalar node indexed by ranges: elementwise ops share their consumer's ranges; reduce opens new ranges and an accumulator. Pass dot_product, reduce_max, reduce_expand, mismatch_reduce.

  6. Read

    tinygrad run_rangeify and pm_apply_rangeify

    After your first version: run_rangeify, the pm_apply_rangeify matcher (line 128) and convert_reduce_to_reduce_with_ranges (line 104).

  7. Implement

    Materialization decision

    Fuse elementwise chains into one loop. Insert a staged temp buffer only when a value is needed under different ranges, e.g. a reduce input that is read twice.

  8. Read

    tinygrad rangeify.py: stage, _limit_bufs, remove_bufferize

    stage() wraps a value in a bufferize over fresh ranges and indexes it back; _limit_bufs (line 169) calls it when a kernel would exceed the device's buffer limit. remove_bufferize (line 46) goes the other way.

  9. Test

    Inspect generated C for reduce(mul(a,b))

    Expect one loop, no temp buffer, and the accumulator as a local scalar.

  10. Measure

    Count kernels/buffers per test

    Print loop count and temp-buffer count per test program; commit the table and fail if it changes unexpectedly.

  11. Test

    10 own tests

    E.g. x minus max(x) (the reduce input is used twice, so it must stage), expand of a reduce, max-reduce of all-negative values (init to INT_MIN, not 0).

Build

A rangeify pass that lowers expand/reduce/rank-1 ALU to scalar loops and decides fusion vs staging.

Portfolio project: kiln v1.3: Fusion plan search with a cost model

kiln, the main project · v1.3 adds fusion search with a cost model, replacing v0.8's fixed fusion rules · builds on v1.2 · next: v1.4

Expose each fuse-or-stage decision as a knob. Enumerate the plans for three rank-1 graphs you can write in Week 4 UIR, estimate bytes moved and flops for each with a cost model, measure real runtime, and report how well the model ranks the plans. This replaces the fixed fusion rules from v0.8.

Deliverables

  • repo with a plan enumerator, a cost model and a runner
  • README with predicted vs measured time and Spearman rank correlation on 3 graphs at n = 2^20 f32: x*recip(sum(x)), x - max(x), and a mean-centered sum of squares
  • the generated C for the chosen plan next to the no-fusion plan, with temp-buffer sizes noted
  • a 600-1200 word write-up on a case where fusing made things slower and why

Rubric

Solid
For each graph the chosen plan is at least as fast as both no-fusion and fuse-everything; Spearman correlation of at least 0.7 between predicted and measured time across all plans.
Exceptional
Cost model includes a cache-size term fitted from your Module 20 bandwidth numbers and the correlation improves measurably; one counterintuitive case explained with measured numbers.

References: TVM: An Automated End-to-End Optimizing Compiler for Deep Learning, How to Scale Your Model: All About Rooflines

Help

If you get stuck

  • A fused reduce is recomputed for every output element: stage a reduce result that is consumed inside another loop.
  • Wrong results after fusion: two reduces share range variables. Give each reduce its own ranges.
  • Accumulator carries over between outputs: initialize it inside the outer loops, not above them.
  • reduce_max wrong on negative inputs: the identity for max is INT_MIN (or -inf for f32), not 0.

Ready to move on when

  • python3 run_tests.py 1 through 4 all pass
  • reduce(mul(a,b)) generates one loop with no temp buffer in the C
  • A reduce input read twice gets exactly one staged buffer
  • 10+ new tests in tests/week04

Talks, papers, code and writing (15)

Lectures

  • Deep Learning Compilers · Raffi Khatchadourian (CUNY Hunter)
    Lecture deck surveying fusion patterns (elementwise, reduction, vertical, horizontal) across TVM, XLA, Inductor and IREE; use it as a map of how other systems decide what to fuse.

Talks

  • Luminal - Search-Based Deep Learning Compilers · Joe Fioti (AI Engineer)
    Describes a compiler that rewrites the graph without a cost model and searches over generated kernels to decide fusion; contrast with tinygrad's heuristic materialization rules.

Papers

  • Triton: An Intermediate Language and Compiler for Tiled Neural Network Computations · Philippe Tillet, H.T. Kung, David Cox
    Shows fusion at tile granularity; read the language and compiler sections.
  • MLIR: A Compiler Infrastructure for the End of Moore's Law · Chris Lattner et al.
    How linalg-style ops carry iteration spaces, the same idea as attaching ranges to ops.
  • Blockbuster, Part 1: Block-level AI Operator Fusion · Microsoft (arXiv 2025)
    A 2025 fusion framework that reasons about which intermediates can stay in local memory; read the worked matmul plus ReLU example.

Blogs and articles

  • Making Deep Learning Go Brrrr From First Principles · Horace He
    The operator fusion section quantifies why staging an elementwise chain costs memory bandwidth.
  • XLA operation semantics · OpenXLA
    Reduce, Broadcast and Reshape definitions in a production IR; check your reduce semantics against Reduce.
  • Introducing Triton: Open-source GPU programming for neural networks · Philippe Tillet (OpenAI)
    The fused softmax example shows a reduce read twice without a staged buffer.
  • A Range Is Not Its Shape: Reading Rangeify-Era tinygrad from OCANNL · Lukasz Stafiniak
    An outside compiler author's reading of tinygrad's rangeify design, contrasting declarative shapes with imperative ranges; read it after rangeify.py for a second view.
  • What is the split strategy for large-dimensional reduction operations in Triton code generation? · PyTorch dev-discuss
    Inductor maintainers explain why one reduction becomes two kernels (split reductions) to fill the GPU; a concrete case where materializing an intermediate is the right call.

Code to read

  • Halide · Halide team
    Tutorial lesson 8 (scheduling multi-stage pipelines) is compute_at/store_at, the exact fuse-or-stage decision.
  • Apache TVM · Apache
    Its operator fusion pass (FuseOps) classifies ops as injective, reduction or opaque, a rule set to compare with yours.
  • Luminal · luminal-ai
    Small primitive-op graph compiler whose search derives fused kernels such as flash attention; read how it represents the primitive op set.

More reading

  • TorchInductor design post — See the answer on op fusion: can_fuse decides legality and score_fusion orders fusions.
